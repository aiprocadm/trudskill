# «Продолжай по ТЗ» — куда идти

Цель навыка: **владелец не должен получать в ответ вопрос — ни «а по какому ТЗ?», ни «как вы хотите?»**. Маршрут определяется правилами ниже; развилки внутри задачи агент решает сам по правилам автономии активного ТЗ.

## Шаг 1. Определить маршрут

| Сказано                                                                                                                           | Куда                                                                |
| --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| «продолжай по ТЗ» **без уточнения**, «доделывай проект», «по миграции», «по переносу», «по CDOPROF», «по календарю», «по задачам» | `docs/TZ_CDOPROF_MIGRATION_STATUS.md` — **активный фронт работ**    |
| «по стабилизации», «по ревью», «по UX», «по блокерам»                                                                             | `docs/TZ_STABILIZATION_UX_STATUS.md` (очередь закрыта — остатки 🟡) |
| «по интерфейсу», «по редизайну», «по UI», «по дизайну»                                                                            | `docs/TZ_UI_REDESIGN_STATUS.md`                                     |
| «по аренде», «по функциям», «по правам», «по эксплуатации»                                                                        | `docs/TZ_ARENDNAYA_SDO_STATUS.md`                                   |
| названа конкретная задача                                                                                                         | Задача важнее очереди: найти её в трекере активного фронта          |
| «проведи аудит», «поищи ошибки», «найди проблемы»                                                                                 | `docs/AUDIT_MODE.md` — режим ревизии, независимо от статуса ТЗ      |

Требования трёх старых ТЗ закрыты. Они отвечают на «как должно выглядеть» (редизайн), «как должно себя вести» (аренда) и задают числа Р1–Р19 (стабилизация), но очереди задач в них нет. **Объём и приоритет работы задаёт ТЗ перехода с CDOPROF.**

## Шаг 2. Прочитать в этом порядке

1. `README.md` §2 «AI Agent State» — дата, ветка, текущая цель.
2. `LMS_AGENT_HANDOFF.md` §1 (дата/ветка) + последние `§5.XX` + §13 Known Issues.
3. **Трекер выбранного ТЗ** — «Где мы сейчас», **«Правила автономии»**, решения РМ1–РМ14 и журнал решений агента, очередь выполнения, статусы задач.
4. Сам текст ТЗ (`TZ_TRUDSKILL_CDOPROF_MIGRATION.md`) по нужной задаче; форму — из ТЗ редизайна, поведение — из «Арендной СДО».

Номер следующего пункта handoff брать **из файла**, а не из README: README отстаёт.

## Шаг 3. Взять работу и доделать

1. Из очереди выполнения взять **первую позицию не в статусе ✅ и не целиком 🚫**. Позиция в 🚫 («ждёт вход владельца») пропускается — берётся следующая.
2. Записать план в `docs/superpowers/plans/YYYY-MM-DD-cdoprof-migration-phase-<N>-<slug>.md`. **Апрув владельца делегирован** (поручение 23.09.2026): план считается утверждённым в момент записи, паузы нет.
3. Реализовать: PR ≤30 файлов, обратимый шаг, зелёный `pnpm ci:check` (+ `test:isolation`, `test:migrations` при миграциях).
4. Обновить трекер и handoff — и **сразу брать следующую позицию**. Сессия работает до исчерпания контекста или очереди, а не до конца одной задачи.

**Развилки решать самому, не спрашивая владельца.** Приоритет выбора: сохранность данных и изоляция → совместимость (контракты/URL/права только добавляются) → обратимость → меньший объём → рекомендация ТЗ. Решение — строкой `РМ-N` в «Журнал решений агента» трекера. Решения РМ1–РМ14 и Р1–Р19 не переоткрываются.

**Нужен вход, которого нет** (ключ API, выгрузки, почтовый провайдер, стенд, продление подписки): код пишется на синтетических фикстурах, живой прогон получает 🚫 и строку в «Что нужно от владельца»; очередь идёт дальше. В финальном сообщении сессии перечислить владельцу открытые пункты «Что нужно от владельца» одним списком — это информирование, не вопрос.

## Шаг 4. Если работы по ТЗ нет

Условие: в четырёх трекерах нет задач в статусах ⬜ 🔎 🟡 ♻️ 🔄 (🚫 не считается — это ожидание владельца) **и** журнал расхождений в `docs/TZ_UI_REDESIGN_STATUS.md` пуст.

Тогда — **режим ревизии** по `docs/AUDIT_MODE.md`, коротко:

1. Взять **класс сверки**, которого нет в реестре прогонов (раздел 6 того файла), и назвать его владельцу до начала проверки. Класс — это «где в системе X может быть не так», проверяемое по всему коду сразу; «пройтись по экранам» классом не является.
2. Приоритет поиска сверху вниз: изоляция тенантов → права fail-open → потеря данных пользователя → неверный расчёт → молчаливый отказ → UX → дрейф → слепая зона.
3. Каждую находку **доказать на коде** и сформулировать сценарий отказа: какие данные → какой неверный результат. Догадка находкой не является.
4. Записать в **журнал расхождений** (`docs/TZ_UI_REDESIGN_STATUS.md`) — журнал в репозитории один.
5. Починить то, что попало в приоритеты 1–5. Остальное — в журнал и, при весе, в `mcp__ccd_session__spawn_task`.
6. **Закрыть класс сторожевым тестом.** Точечная починка без сторожа класс не закрывает — проверено на записи 278, вернувшейся через три недели записью 389.
7. Дописать строку в реестр прогонов, даже если результат «чисто».

## Границы (одинаковы для всех режимов)

- Не править исторические миграции, не удалять и не переименовывать поля контрактов `packages/api-contracts`, не менять смысл существующих прав и URL. **Добавления, перечисленные в ТЗ перехода с CDOPROF** (роли `curator`/`viewer`, новые права §12, ручки §16, необязательные поля, маршруты `/tasks`, `/calendar`, `/curator`, `/settings/import-cdoprof`, редирект календаря окончаний), **уже разрешены владельцем** — отдельного решения не требуют.
- Не ослаблять сторожевые тесты. `ia-architecture.e2e.test.ts` — жёсткий инвариант; для ТЗ перехода конфликт решается выбором варианта, который в него укладывается, с записью решения.
- Сроки, пороги, лимиты, числа попыток — настройки со значением по умолчанию, не константы в коде.
- Наборы прав брать из `iam.role_permissions` живой базы, а не из названия роли и не из текста ТЗ.
- Необратимое (финальная миграция на боевом контуре, отключение CDOPROF, удаление данных, письма реальным людям) — только владелец; агент готовит runbook.
- Ключи API и выгрузки с ПДн в репозиторий не попадают — только env / стенд.
