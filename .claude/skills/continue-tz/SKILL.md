# «Продолжай по ТЗ» — куда идти

Цель навыка: **владелец не должен получать в ответ вопрос «а по какому ТЗ?»**. Маршрут определяется правилами ниже; вопрос задаётся только там, где он прямо предписан.

## Шаг 1. Определить маршрут

| Сказано                                                                                    | Куда                                                            |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| «продолжай по ТЗ» **без уточнения**, «по стабилизации», «по ревью», «по UX», «по блокерам» | `docs/TZ_STABILIZATION_UX_STATUS.md` — **активный фронт работ** |
| «по интерфейсу», «по редизайну», «по UI», «по дизайну»                                     | `docs/TZ_UI_REDESIGN_STATUS.md`                                 |
| «по аренде», «по функциям», «по правам», «по эксплуатации»                                 | `docs/TZ_ARENDNAYA_SDO_STATUS.md`                               |
| названа конкретная задача                                                                  | Задача важнее очереди: найти её в трекере активного фронта      |
| «проведи аудит», «поищи ошибки», «найди проблемы»                                          | `docs/AUDIT_MODE.md` — режим ревизии, независимо от статуса ТЗ  |

Требования двух старых ТЗ закрыты. Они отвечают на «как должно выглядеть» (редизайн) и «как должно себя вести» (аренда), но очереди задач в них нет. **Объём и приоритет работы задаёт ТЗ стабилизации.**

## Шаг 2. Прочитать в этом порядке

1. `README.md` §2 «AI Agent State» — дата, ветка, текущая цель.
2. `LMS_AGENT_HANDOFF.md` §1 (дата/ветка) + последние `§5.XX` + §13 Known Issues.
3. **Трекер выбранного ТЗ** — раздел «Где мы сейчас», затем очередь выполнения и статусы задач.
4. Сам текст ТЗ по нужной задаче.

Номер следующего пункта handoff брать **из файла**, а не из README: README отстаёт.

## Шаг 3. Взять работу

Из трекера активного фронта берётся **первая незакрытая позиция очереди выполнения**, а не понравившаяся задача. Исключения из очереди прописаны в самом ТЗ: 15.1 (сбор ошибок) делается вместе с фазой 1, 13.4 (изоляция тенантов) — до работ по поиску 3.6.

Перед кодом: **план в `docs/superpowers/plans/` + апрув владельца.** Фаза = один PR = один обратимый шаг, ≤30 файлов, зелёный `pnpm ci:check`.

## Шаг 4. Если работы по ТЗ нет

Условие: в трёх трекерах нет задач в статусах ⬜ 🔎 🟡 ♻️ **и** журнал расхождений в `docs/TZ_UI_REDESIGN_STATUS.md` пуст.

Тогда — **режим ревизии** по `docs/AUDIT_MODE.md`, коротко:

1. Взять **класс сверки**, которого нет в реестре прогонов (раздел 6 того файла), и назвать его владельцу до начала проверки. Класс — это «где в системе X может быть не так», проверяемое по всему коду сразу; «пройтись по экранам» классом не является.
2. Приоритет поиска сверху вниз: изоляция тенантов → права fail-open → потеря данных пользователя → неверный расчёт → молчаливый отказ → UX → дрейф → слепая зона.
3. Каждую находку **доказать на коде** и сформулировать сценарий отказа: какие данные → какой неверный результат. Догадка находкой не является.
4. Записать в **журнал расхождений** (`docs/TZ_UI_REDESIGN_STATUS.md`) — журнал в репозитории один.
5. Починить то, что попало в приоритеты 1–5. Остальное — в журнал и, при весе, в `mcp__ccd_session__spawn_task`.
6. **Закрыть класс сторожевым тестом.** Точечная починка без сторожа класс не закрывает — проверено на записи 278, вернувшейся через три недели записью 389.
7. Дописать строку в реестр прогонов, даже если результат «чисто».

## Границы (одинаковы для обоих режимов)

- Не править исторические миграции, контракты `packages/api-contracts`, RBAC-модель и URL маршрутов — только решением владельца.
- Не ослаблять сторожевые тесты. `ia-architecture.e2e.test.ts` — жёсткий инвариант: конфликт с ним → остановиться и спросить.
- Решения Р1–Р19 ТЗ стабилизации не переоткрывать: при невыполнимости описать препятствие и предложить замену.
- Сроки, пороги, лимиты, числа попыток — настройки со значением по умолчанию, не константы в коде.
- Наборы прав брать из `iam.role_permissions` живой базы, а не из названия роли и не из текста ТЗ.

## В конце сессии

README §2 → новый `§5.XX` в `LMS_AGENT_HANDOFF.md` → статусы и журнал сессий в трекере своего ТЗ → (для ревизии) строка в реестре классов. Полный протокол — `docs/DOCUMENTATION_MAP.md#agent-handoff-protocol`.
