# Резервное копирование и откат

**Состояние на 2026-08-08 (Фаза 6 Task 4):** скрипты написаны и проверены вживую —
копия снимается, порча обнаруживается, из копии поднимается работоспособная база.
**Что осталось за владельцем:** поставить строки в `crontab` на сервере и решить, куда
класть копию вне сервера (см. «Что нужно сделать один раз»).

## Чем снимаем и чем проверяем

| Скрипт                     | Что делает                                                            | Когда запускать                          |
| -------------------------- | --------------------------------------------------------------------- | ---------------------------------------- |
| `infra/backup.sh`          | Дамп базы + снимок файлов MinIO, проверка целостности, чистка старого | ежедневно, 03:00                         |
| `infra/backup-watchdog.sh` | Проверяет, что копия свежая, целая и что есть место под следующую     | ежедневно, 04:30                         |
| `infra/restore-drill.sh`   | Учения: поднимает копию в ОДНОРАЗОВОЙ базе и проверяет данные         | еженедельно + перед крупными изменениями |

Все три сообщают о беде **ненулевым кодом возврата** — этого достаточно, чтобы cron
прислал письмо. Если задать `CDOPROF_ALERT_CMD`, тот же текст уйдёт в выбранный канал.

## Что нужно сделать один раз (владелец)

1. **Поставить в `crontab`** (пути подставить свои):

   ```cron
   0 3 * * *  cd /path/to/repo && infra/backup.sh          >> /var/log/cdoprof-backup.log 2>&1
   30 4 * * * cd /path/to/repo && infra/backup-watchdog.sh >> /var/log/cdoprof-backup.log 2>&1
   0 5 * * 1  cd /path/to/repo && infra/restore-drill.sh   >> /var/log/cdoprof-restore-drill.log 2>&1
   ```

2. **Задать переменные окружения** под свою топологию. На стенде (systemd + общий
   контейнер Postgres) это:

   ```bash
   CDOPROF_PG_EXEC="docker exec -i test-postgres"
   POSTGRES_USER=trudskill_stand_app
   POSTGRES_DB=trudskill_stand
   CDOPROF_MINIO_VOLUME=infra_minio-data
   CDOPROF_BACKUP_DIR=/var/backups/cdoprof
   ```

   На прод-стеке (docker compose) достаточно значений по умолчанию — они рассчитаны
   именно на него.

3. **Решить про копию вне сервера** (вопрос №C плана Фазы 6). Пока `CDOPROF_OFFSITE_CMD`
   пуст, копия лежит на том же диске, что и данные: пожар или отказ диска уносит и то,
   и другое. Команда получает путь к файлу, например:

   ```bash
   CDOPROF_OFFSITE_CMD='rclone copy --config /root/rclone.conf'
   ```

## Целевые показатели

Из ТЗ §12.3 (пилот): **RTO 4 часа**, **RPO 24 часа**. Отсюда суточное расписание.

**Измерено на учениях 2026-08-08:** восстановление базы стенда из копии — **8 секунд**
(150 таблиц, 80 миграций). Это только часть RTO: остальное — поднять сервисы и проверить
работу; но именно эта часть раньше была непроверенной.

## Порядок восстановления

1. Взять свежую копию: `ls -1t /var/backups/cdoprof/db-*.sql.gz | head -1`.
2. Убедиться, что она цела: `infra/restore-drill.sh /путь/к/копии` — учения идут в
   одноразовой базе и ничего не портят.
3. Создать (если нужно) роль приложения и пустую базу, **восстанавливать под ролью
   приложения**: дамп снимается без владельцев и прав, поэтому все объекты достанутся
   тому, кто восстанавливает.

   ```bash
   gunzip -c db-СНИМОК.sql.gz | psql -v ON_ERROR_STOP=1 -U <роль_приложения> -d <база>
   ```

4. Файлы MinIO — из снимка тома:

   ```bash
   docker run --rm -v <том>:/data -v /var/backups/cdoprof:/backup alpine \
     sh -c 'cd /data && tar xzf /backup/minio-СНИМОК.tar.gz'
   ```

5. Поднять сервисы и проверить: вход, кабинет слушателя, выдача документа.

**Почему дамп без владельцев и прав.** Первые же учения показали: обычный дамп на чистом
сервере **не восстанавливается** — он требует роль, которой там нет, и psql обрывается на
первой строке. Кроме того, кластер Postgres на стенде общий с другими проектами, и
выгрузка глобальных ролей положила бы в нашу копию чужие учётные записи.

## Откат релиза

1. Выкатка снимает дамп ДО применения миграций (`.github/workflows/deploy.yml`), поэтому
   точка возврата есть всегда. Неудачный дамп останавливает выкатку.
2. Откат кода: вернуть предыдущий образ/коммит и перезапустить стек.
3. Откат данных нужен, только если миграция необратима, — тогда восстановление по
   порядку выше из дампа, снятого перед выкаткой.
