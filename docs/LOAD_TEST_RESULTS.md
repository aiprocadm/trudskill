# Замеры нагрузки против §12 ТЗ

**Дата прогона:** 2026-08-09. **Стенд:** 8 ядер, 47 ГБ, база общая с другими проектами.
**Отдельный тенант:** `load-pilot` (`t_a79d1f5df60e`), 500 слушателей, залитых **обычным
массовым импортом** — тем же кодом, что в бою.

Оснастка: `infra/load/seed-load-tenant.sh` (подготовка) + `infra/load/k6-pilot.js` (прогон).
Прогон повторяем: те же две команды дают те же условия.

## Что требует §12

| Требование                                        | Значение |
| ------------------------------------------------- | -------- |
| §12.1 активных слушателей на тенант               | 300–500  |
| §12.1 параллельных экзаменационных сессий         | 20–50    |
| §12.1 **p95 API списков**                         | < 300 мс |
| §12.4 пакет документов на группу из 25 слушателей | ≤ 2 мин  |

## Что показали замеры

### Один запрос списка (без конкуренции)

| Тенант             | До правок | После правок |
| ------------------ | --------- | ------------ |
| демо (2 слушателя) | 0,056 с   | 0,021 с      |
| нагрузочный (500)  | 0,67 с    | 0,060 с      |

### Под нагрузкой (p95 по спискам)

| Одновременных сессий | Исходно     | 1-й заход | 2-й заход | 3-й заход      | Требование |
| -------------------- | ----------- | --------- | --------- | -------------- | ---------- |
| 50 (верх диапазона)  | **30,25 с** | 2,32 с    | 0,79 с    | **0,378 с**    | 0,3 с      |
| 20 (низ диапазона)   | не мерилось | 0,485 с   | 0,152 с   | **0,042 с** ✅ | 0,3 с      |

Пропускная способность: 1,4 → 21 → 45 → **59 запросов в секунду** (в 42 раза). Ошибок нет
ни в одном из шести прогонов (последние: 0 из 10 720 и 0 из 6370).

**Вывод: требование §12.1 ВЫПОЛНЕНО на нижней границе диапазона (20 сессий) с семикратным
запасом и пока НЕ выполнено на верхней (50 сессий) — 0,378 с против 0,3 с.** Разрыв
сократился со стократного до 1,26-кратного.

## Что нашли и починили по факту замеров

**Главное: обычное ЧТЕНИЕ списка переписывало всё состояние центра.**
Состояние сохранялось в конце каждого запроса — включая тот, который ничего не менял.
При 500 слушателях это «удалить всё и вставить заново» на каждый показ страницы.
Причём вставка шла **по одной строке**: больше тысячи обращений к базе на один клик.

Две точечные правки (обе — в `postgres-mvp-persistence.backend.ts`):

1. **Не сохранять, если ничего не менялось.** При загрузке снимается отпечаток состояния,
   в конце запроса он сравнивается. Совпал — писать нечего. Отпечаток считается по
   открытым значениям в памяти: шифрование ПДн даёт каждый раз разный шифртекст, сравнивать
   его бессмысленно.
2. **Вставка пачками по 500 строк** вместо построчной.

Результат первого захода: одиночный запрос ускорился в 11 раз, p95 под нагрузкой — в 13 раз.

### Второй заход (2026-08-09): чтение одним запросом вместо полусотни

Замер показал следующее по величине: загрузка состояния шла **циклом по коллекциям** — на
каждую свой `select`. Коллекций около пятидесяти, то есть полсотни обращений к базе на
КАЖДЫЙ запрос пользователя, включая простой показ списка. При этом всё состояние центра с
500 слушателями читается **одним** запросом за 2,8 мс.

Правка: один `select` на весь тенант с группировкой по коллекциям в памяти. Результат:
одиночный запрос 0,060 → 0,035 с, p95 при 50 сессиях 2,32 → 0,79 с, пропускная способность
21 → 45 запросов в секунду.

Попутно проверено, а не предположено: расшифровка ПДн (AES) стоит микросекунды на запись и
главным расходом не является.

### Третий заход (2026-08-09): ленивая раскладка коллекций

Замер второго захода показал: запрос к базе стоит 3 мс, подсчёт отпечатка состояния 7,4 мс
(дважды за запрос), остальное — раскладка 1504 записей по полусотне коллекций с расшифровкой
ПДн всех слушателей. При этом **обычный запрос списка трогает одну-две коллекции из
полусотни**: списку слушателей не нужны ни история статусов зачислений (500 записей), ни
кэши идемпотентности.

Правка: сырые строки кладутся в состояние как есть, а раскладываются по первому обращению —
и только те, к которым обратились. Отпечаток снимается по коллекциям в момент раскладки,
поэтому сравнивается только тронутое. Записываются в базу только изменившиеся коллекции.
**Ни один сервис не переписан** — они как читали `state.learners`, так и читают.

Результат: одиночный запрос 0,035 → 0,020 с, p95 при 50 сессиях 0,79 → 0,378 с, при
20 сессиях 0,152 → 0,042 с, пропускная способность 45 → 59 запросов в секунду.

Попутно сохранено важное свойство: старые строки с незашифрованными ПДн по-прежнему
перешифровываются при ближайшем сохранении. В памяти они выглядят как расшифрованные и по
отпечатку сошли бы за «не менялись» — коллекция помечается к записи явно. Это поймал
существующий тест, а не ревью.

### Где узкое место сейчас (замер 2026-08-09, после третьего захода)

Гипотезу проверили инструментом, а не рассуждением: под нагрузкой в 50 сессий процесс
бэкенда занимает **94% одного ядра** (мгновенный замер `top`, два подряд: 94,1% и 94,5%).
При этом на машине восемь ядер.

**Вывод: упираемся не в базу и не в код, а в то, что бэкенд — ОДИН процесс.** Node
выполняет запросы по очереди в одном потоке; 59 запросов в секунду × ~16 мс работы над
каждым и есть те самые 94% ядра. Остальные семь ядер простаивают.

Отсюда следующий шаг — не оптимизация кода, а **запуск нескольких экземпляров бэкенда за
обратным прокси**. Это стало безопасным именно сейчас: Фаза 6 Task 9 закрыла миграции
блокировкой уровня сеанса, а все планировщики берут свои блокировки — то есть второй
экземпляр не накатит миграции повторно и не задвоит ночные задачи.

Осторожно с двумя замерами, которые легко принять за правду:

- `ps -o pcpu` даёт **среднее за всю жизнь процесса**, а не текущую загрузку: на том же
  прогоне он показал 37% вместо 94%. Мгновенную загрузку берём вторым замером `top`.
- Токен доступа живёт 15 минут. Прогон с протухшим токеном показал «p95 = 9 мс и 86
  запросов в секунду» — и это были 100% отказов, отбитых на входе. Всегда проверять
  `checks` и `http_req_failed`, прежде чем радоваться числам.

## Что осталось и почему это отдельная задача

Остаток объясняется тем, что **каждый запрос по-прежнему загружает состояние центра
целиком**: демо-тенант (2 слушателя) — 21 мс, нагрузочный (500) — 60 мс на одном и том же
коде. Разница и есть цена чтения всего состояния плюс расшифровки ПДн всех пятисот
слушателей. Под 50 одновременными сессиями эта цена умножается.

До требования на верхней границе осталось около 20% (0,336–0,378 с против 0,3 с;
воспроизводится стабильно в трёх прогонах).

Порядок дальнейших шагов теперь определён замером, а не догадкой:

1. **Несколько экземпляров бэкенда за прокси** — самый дешёвый шаг: кода не трогает вовсе,
   а свободных ядер семь из восьми. Требует правки `infra/docker-compose.prod.yml` и
   `infra/Caddyfile` плюс проверки, что метрики и отметки планировщиков собираются со всех
   экземпляров.
2. **Постраничное чтение списков из базы** — если после (1) не хватит: сейчас показ первых
   50 слушателей всё ещё поднимает в память все 500. Это переписывание сервисов, поэтому
   браться за него стоит только по цифрам, оставшимся после (1).

Важная оговорка про условия замера: стенд делит машину с пятью другими проектами, средняя
загрузка процессора на старте прогона была около 4 из 8. На выделенной машине числа будут
лучше, но проверять это надо замером, а не рассуждением.

**Предложение по объёму** (для следующей задачи, не сделано здесь):

- читать по требованию только те коллекции, которые запросу действительно нужны;
- расшифровывать ПДн лениво — сейчас расшифровываются все 500 слушателей даже для списка,
  где ПДн не показываются;
- постранично читать списки из базы вместо среза массива в памяти.

## §12.4: пакет документов на 25 человек — оснастка готова, замер ждёт курса

**Числа до сих пор нет, и это сказано прямо.** Замер требует не данных, а полностью
настроенного курса, которого на стенде нет: в демо-центре есть программы, группа и комиссия,
но **нет набора документов курса** (`courseDocumentSets`) — значит выпускать нечего.

Что должно быть готово, чтобы замер вообще запустился (это требования продукта, а не
скрипта):

1. Программа с опубликованной версией и паспортом.
2. Набор документов курса с шаблонами и правилами нумерации.
3. Комиссия и действующая лицензия центра.
4. Группа из 25 слушателей с завершёнными зачислениями.

Оснастка написана: `infra/load/measure-document-package.sh`. Она меряет то, что чувствует
человек, — не «ручка ответила», а **время до момента, когда все задачи документов группы
завершились**. Перелёт за 2 минуты даёт ненулевой код возврата: замер должен краснеть, а не
сообщать «ну почти».

```bash
BASE_URL=http://127.0.0.1:3011/api/v1 TENANT_ID=<тенант> GROUP_ID=<группа> \
  TOKEN=<jwt> infra/load/measure-document-package.sh
```

Если подготовки не хватает, скрипт не молчит и не врёт нулём: он печатает код отказа и
отсылает к перечню выше.

## Как повторить

```bash
# 1. Подготовить тенант и данные
PLATFORM_PASSWORD='<пароль платформенного администратора>' LEARNERS=500 \
  infra/load/seed-load-tenant.sh

# 2. Получить токен администратора нагрузочного тенанта и прогнать профиль
k6 run -e BASE_URL=http://127.0.0.1:3011/api/v1 -e TENANT_ID=<id> \
       -e TOKEN=<jwt> -e VUS=50 -e DURATION=2m infra/load/k6-pilot.js
```

Порог `p95 < 300 мс` зашит в профиль как условие провала: прогон, который «почти уложился»,
краснеет и возвращает ненулевой код.
