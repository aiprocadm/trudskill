# Статус выполнения ТЗ «Переход с CDOPROF на TrudSkill»

Трекер прогресса по [TZ_TRUDSKILL_CDOPROF_MIGRATION.md](../TZ_TRUDSKILL_CDOPROF_MIGRATION.md) (ТЗ от 23.09.2026, версия 1.0; основание — обследование аккаунта CDOPROF и аудит репозитория на `ac9eb8b`). Описание API источника — [docs/audit/cdoprof-openapi-v1.yaml](./audit/cdoprof-openapi-v1.yaml).

**Это активный фронт работ репозитория с 23.09.2026.** По фразе «продолжай по ТЗ» без уточнения агент идёт сюда — правило маршрутизации в [DOCUMENTATION_MAP.md#tz-routing](./DOCUMENTATION_MAP.md#tz-routing). Очередь ТЗ стабилизации закрыта по коду (handoff §5.548 и далее); три предыдущих ТЗ остаются **каноном по своему предмету**.

**Цель, к которой ведёт очередь:** учебный центр работает в TrudSkill вместо CDOPROF — данные перенесены, кураторы ведут группы, документы и задачи в TrudSkill, CDOPROF отключён.

## Где мы сейчас (23.09.2026)

**Фаза: 0 закрыта по коду 23.09.2026 (§5.553, §5.554). Следующее действие — позиция 4 очереди** (аддитивные миграции без изменения поведения: роль `curator` + права, `legacy_ids`/`import_runs`, `external_id/source_system`, схема `tasks`).

**Позиция 3 (спайк) — блокер хранения подтверждён числами (§5.554, `docs/LOAD_TEST_RESULTS.md` 2026-09-23):** на 25 000 групп / 14 000 слушателей один `GET /groups` — p95 1,7 с, при 10 пользователях — 14 с (бюджет 0,5 с); 0,37 с из них — сама передача 25 МБ снимка из Postgres. Оснастка для замера «после» Фазы 1: `pnpm perf:synth` + `infra/load/k6-cdoprof-volume.js`, база `trudskill_perf` оставлена.

Позиция 2 сделана: план `docs/superpowers/plans/2026-09-23-cdoprof-migration-phase-0-audit.md`, модуль `apps/backend/src/modules/import-cdoprof/` (схемы, HTTP-транспорт с паузами и повторами, клиент только на чтение, обезличенные фикстуры под сторожем, выгрузка в JSON с манифестом без ПДн), скрипт `pnpm export:cdoprof` (`--fixtures` — без сети и ключа), описание источника `docs/audit/cdoprof-source-2026-09.md`. **Живой прогон на стенде — 🚫 О1** (ключ API + IP); чек-лист того, что он закроет, — §6 описания источника.

Что нужно знать перед первой фазой:

1. **Главный технический блокер — слой хранения** (ТЗ §0 п. 3, §15.1): домен живёт JSON-снимком на тенант и целиком грузится на каждый запрос. На объёме CDOPROF (≈25 000 групп, ≈14 000 слушателей) это не заработает. Поэтому Фаза 1 идёт первой среди больших фаз, а до неё — только безопасные PR, которые не трогают снимок (позиции 2–6).
2. **Живых данных CDOPROF у агента нет** (ключ API, выгрузки Excel, образцы ЕИСОТ/ФРДО — у владельца). Это не останавливает работу: весь код импорта и сверки строится на **обезличенных синтетических фикстурах** по описанию API и колонкам выгрузок; живой прогон — отдельная строка со статусом 🚫 (см. «Правила автономии», п. 4).
3. **Номера миграций в ТЗ (0099…0113) — предложения.** Брать следующий свободный номер на момент работы (на 23.09.2026 последняя — `0098_audit_log_query_indexes.sql`).

## Правила автономии (поручение владельца от 23.09.2026)

Владелец поручил: **вопросы, требующие его решения, агент решает сам, выбирая наиболее эффективный вариант; фраза «продолжай по ТЗ» должна доделывать проект.** Отсюда:

1. **Владельцу вопросов не задавать.** При развилке выбрать вариант по приоритетам сверху вниз: (1) сохранность данных и изоляция тенантов → (2) совместимость: не ломать контракты `packages/api-contracts`, URL и существующие права — только добавлять → (3) обратимость (флаг, аддитивная миграция, редирект) → (4) меньший объём при той же пользе → (5) рекомендация самого ТЗ. Решение записать строкой в «Журнал решений агента» (`РМ15`, `РМ16`, …) с причиной — одной строкой.
2. **План фазы — обязателен, апрув — делегирован.** План пишется в `docs/superpowers/plans/YYYY-MM-DD-cdoprof-migration-phase-<N>-<slug>.md` и считается утверждённым в момент записи; паузы на апрув нет. Правило CLAUDE.md «план + апрув владельца» для этого ТЗ выполняется этим поручением.
3. **Этим ТЗ уже разрешены** (решение владельца в смысле CLAUDE.md «Границы»): новые роли `curator` и `viewer` и новые права из §12; новые ручки из §16 и новые **необязательные** поля в контрактах; новые маршруты `/tasks`, `/calendar`, `/curator`, `/settings/import-cdoprof` и редирект `/learning/calendar → /calendar?types=deadline`; новые схемы и таблицы §17. **Не разрешено и по-прежнему запрещено:** удалять/переименовывать существующие поля контрактов, менять смысл существующих прав, править исторические миграции, ослаблять сторожевые тесты.
4. **Внешние блокеры не останавливают очередь.** То, что физически может сделать только владелец (ключ API, выгрузки, продление подписки, провайдер почты, боевой стенд, приёмка сверки), получает статус **🚫 ждёт вход** и строку в разделе «Что нужно от владельца». Агент **сразу берёт следующую незаблокированную позицию**. Код для заблокированной части пишется заранее на синтетических фикстурах, чтобы по приходе входа оставался один запуск.
5. **Работать до конца сессии, а не до конца одной задачи.** Закрыл позицию (зелёный `pnpm ci:check`, PR, обновлён трекер) — бери следующую. Фаза = один или несколько PR, каждый ≤30 файлов, каждый — обратимый шаг.
6. **Необратимое — только владелец.** Финальная миграция на боевом контуре, заморозка ввода в CDOPROF, отключение CDOPROF, удаление данных, отправка писем реальным людям — агент готовит runbook и команды, но не выполняет.
7. **Решения РМ1–РМ14 не переоткрываются.** Если решение оказалось невыполнимым — описать препятствие и принять замену новой строкой журнала решений (не спрашивать).
8. **Сверка и журнал расхождений — как везде** (CLAUDE.md «Сверка логики с ТЗ»): найденное вне задачи — в журнал расхождений [TZ_UI_REDESIGN_STATUS.md](./TZ_UI_REDESIGN_STATUS.md), дефекты логики (изоляция, fail-open прав, потеря данных) — чинить сразу.
