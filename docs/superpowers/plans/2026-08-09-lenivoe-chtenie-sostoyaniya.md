# План: ленивое чтение состояния тенанта (закрыть §12.1 на 50 сессиях)

**Статус:** ✅ Task 1 и Task 2 выполнены 2026-08-09; Task 3 (сторожа) — там же.
**Основание:** замеры `docs/LOAD_TEST_RESULTS.md`; требование §12.1 ТЗ.
**Дата:** 2026-08-09.

## Зачем

Требование §12.1 — «p95 API списков < 300 мс при 300–500 слушателях и 20–50 параллельных
сессиях». Сейчас:

| Одновременных сессий | p95        | Требование |
| -------------------- | ---------- | ---------- |
| 20 (низ диапазона)   | 0,152 с ✅ | 0,3 с      |
| 50 (верх диапазона)  | 0,79 с ❌  | 0,3 с      |

Два предыдущих захода (не сохранять при чтении, вставка пачками, чтение одним запросом)
дали ускорение в 38 раз — с 30,25 с до 0,79 с. Дальше точечными правками не обойтись.

## Что именно осталось дорогим (измерено, а не предположено)

На запрос к центру с 500 слушателями (всего 1504 записи состояния, ~400 КБ):

| Что                                    | Цена      | Комментарий                                      |
| -------------------------------------- | --------- | ------------------------------------------------ |
| Запрос к базе (один, весь тенант)      | ~3 мс     | Уже дёшево, трогать нечего                       |
| Подсчёт отпечатка состояния (два раза) | ~7,4 мс   | По разу при загрузке и при сохранении            |
| Материализация 1504 записей в массивы  | остальное | Главный расход: копии объектов + расшифровка ПДн |

Ключевое наблюдение: **обычный запрос списка трогает одну-две коллекции из полусотни.**
Показ списка слушателей не нуждается ни в истории статусов зачислений (500 записей), ни в
кэшах идемпотентности, ни в сорока остальных коллекциях — но платит за них полностью.

## Замысел

**Читать всё одним запросом (как сейчас), но раскладывать по коллекциям ЛЕНИВО — только те,
к которым запрос реально обратился.**

Почему именно так, а не «постраничные SQL-запросы на каждый список»:

- запрос к базе уже стоит 3 мс и не является проблемой — переписывать чтение на SQL-выборки
  пришлось бы во всех сервисах сразу, это месяцы работы и риск для всех сценариев;
- дорога именно материализация, а её можно отложить **без изменения кода сервисов**: они
  как обращались к `state.learners`, так и будут;
- отпечаток тогда считается только по тронутым коллекциям — нетронутая измениться не могла.

Ожидаемый эффект: обычный запрос списка перестаёт платить за 40+ чужих коллекций.

## Задачи

### Task 1 — Ленивая раскладка состояния

**Files:** `apps/backend/src/modules/mvp/infrastructure/in-memory-mvp.state.ts`,
`postgres-mvp-persistence.backend.ts`, `mvp-collections.ts`

**Tasks:**

- [x] В состоянии коллекции становятся ленивыми: значение раскладывается при первом
      обращении из уже прочитанных «сырых» строк. Ссылка на массив стабильна — сервисы
      мутируют его как раньше (`push`, `splice`).
- [x] Загрузка кладёт в состояние сырые строки, а не готовые массивы.
- [x] Отпечаток считается **только по тронутым** коллекциям; нетронутые в сравнении
      участвуют как «не менялись».
- [x] Сохранение переписывает только тронутые коллекции (нетронутая не могла измениться).

**Acceptance:** ни один сервис не переписан; все существующие тесты MVP зелёные; на списке
слушателей материализуется одна коллекция вместо полусотни.

**Риск и как его снимаем:** это ядро, которым пользуется весь модуль MVP. Поэтому — ноль
изменений в сервисах, и полный прогон `pnpm test:backend` как условие приёмки, а не как
формальность.

### Task 3 — Сторож против возврата беды

**Tasks:**

- [x] Тест, закрепляющий: чтение списка не материализует чужие коллекции.
- [x] Тест, закрепляющий: сохранение не трогает коллекции, к которым не обращались.

**Выполнено 2026-08-19** (§5.306): `lazy-state.perf.test.ts`, 7 проверок. Проверено подсадным
нарушителем — возврат жадной раскладки роняет 4 из 7. Заодно замер объяснил, почему ленивость
здесь единственный путь: расшифровка одного СНИЛС стоит ~64 мкс, и это цена СРЕДЫ, а не кода
(чистый Node на `aes-256-gcm` даёт столько же). На 500 слушателях — 27–32 мс на КАЖДЫЙ запрос.
Оптимизировать саму расшифровку бессмысленно; не платить можно только не трогая коллекцию.

**Acceptance:** правка, возвращающая жадную загрузку, роняет тесты.

## Чего в этой работе НЕ будет

- Переписывания сервисов на SQL-выборки: это отдельная большая работа, и замер пока не
  показывает, что она нужна.
- Кэша состояния между запросами: с несколькими экземплярами бэкенда это источник
  рассинхронизации, а выигрыш не измерен.
- Изменения формата хранения: миграции здесь не нужны вовсе.

## Открытый вопрос владельцу

Требование §12.1 названо для «пилотной нагрузки». Стоит ли добиваться 300 мс именно на
верхней границе (50 одновременных экзаменов) **сейчас**, или достаточно того, что нижняя
граница взята с двукратным запасом, а верхняя закрыта на будущее? От ответа зависит, делать
ли Task 1 сразу или после приёмки фаз.

переписывание сервисов — отдельное решение, отдельная задача.
