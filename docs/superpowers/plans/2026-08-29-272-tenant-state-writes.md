# План программы 272+292 — запись состояния арендатора

Решение и разбор вариантов: `docs/superpowers/specs/2026-08-29-272-tenant-state-writes.md`.
Каждый срез = один PR = зелёный `pnpm ci:check`.

## Срез 1 — версия состояния арендатора

**Файлы:** миграция `0087_tenant_state_versions.sql`; `in-memory-mvp.state.ts`,
`in-memory-documents.state.ts` (поле версии); `postgres-mvp-persistence.backend.ts`,
`postgres-documents-persistence.backend.ts` (чтение/сверка); общий помощник сверки;
перехватчики запросов (409); тесты.

**Задачи:**

- [ ] Таблица `core.tenant_state_versions (tenant_id, scope, version, updated_at)`.
- [ ] Загрузка кладёт прочитанную версию на объект состояния (`stateVersion`).
- [ ] Сохранение в ТОЙ ЖЕ транзакции увеличивает версию условно; ноль строк = конфликт.
- [ ] Конфликт → `ConflictException` с человеческим текстом и кодом `tenant_state_conflict`.
- [ ] Метрика `tenant_state_conflict_total` с ярлыком `scope`.

**Приёмка:** тест-гонка двух сохранений мимо замка (второй падает, первый цел); обычный
прогон не краснеет; версия НЕ растёт, когда запрос ничего не менял.

## Срез 2 — заявка на номер документа в БД

**Файлы:** миграция `0088_documents_issued_number_claims.sql`;
`postgres-documents-persistence.backend.ts`; тесты.

**Задачи:**

- [ ] Таблица `documents.issued_number_claims` с PK `(tenant_id, reserved_number)`.
- [ ] При записи коллекции `reservations` заявлять номера; чужая заявка = конфликт.
- [ ] Переиспользование освобождённого номера ТЕМ ЖЕ резервированием не ломается.

**Приёмка:** тест «два состояния выпускают один номер» — второе сохранение падает;
тест «упавшая задача освободила номер, он переиспользован» — проходит.

## Итог (2026-08-29) — ПРОГРАММА ЗАКРЫТА

Срезы 1 и 2 влиты (PR #634, #635), закрывающий — этот. Обе линии обороны на месте и проверены
на настоящем PostgreSQL (12 проверок) плюс мутацией продукта.

Отклонение от плана: срез 1 попутно закрыл дрейф «чтение документов пишет снимок на каждый
запрос» (журнал 299) — он мешал самой версии: запрос, ничего не менявший, двигал бы версию и
отбирал право записи у того, кто менял.

Что НЕ сделано и почему — в спецификации: построчной записи нет, автоповтора при конфликте
нет. Живой прогон в два экземпляра не делался: нужен стенд и замер доли 409 по метрике
`tenant_state_conflict_total`.
