# Контакты, сотрудники и представитель компании (МГ-D2) — Фаза 2, срезы 14.1–14.4 — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking. План утверждён по поручению владельца (правила автономии ТЗ перехода).

**Goal:** ТЗ перехода МГ-D2.1 [P0]: у компании — контактные лица и сотрудники (таблицы `crm.counterparty_contacts` и `crm.counterparty_employees` созданы в 0002, но мёртвые), массовое добавление сотрудников, связь «сотрудник → слушатель», приглашение контакта представителем в портал заказчика; в мастере группы — «слушатели из сотрудников компании» (отложено РМ53).

**Architecture:** Разведка (§5.600): никакой код не читает и не пишет эти таблицы; у контактов нет `user_id` и статуса, у сотрудников — `learner_id`; ограничение `UNIQUE NULLS NOT DISTINCT (tenant_id, counterparty_id, employee_no)` не даёт завести второго сотрудника без табельного номера. Проекция снимка в `crm.counterparties` пишется всегда, но **родительская строка не гарантирована** (проецируются только изменённые, сбой проекции глотается, в режиме памяти таблиц нет). Поэтому:

- контакты и сотрудники — **прямо в Postgres** (как задачи и представления, а не коллекция снимка): объёмы CDOPROF — тысячи сотрудников;
- компания проверяется по снимку (источник правды, скоуп представителя), а перед записью репозиторий **в той же транзакции досоздаёт строку компании** той же проекцией (`projectEntity` + `upsertRows`) — внешние ключи 0003 остаются в силе;
- в режиме памяти (`ALLOW_IN_MEMORY_STATE`) — репозиторий в памяти (образец `saved-views`).

Срезы:

- **14.1 (бэкенд):** миграция `0116_crm_contacts_employees_activate.sql` (контакты: `user_id`, `status` active/archived, `external_id`, `source_system`; сотрудники: `learner_id` + индекс; табельный номер уникален только когда задан); модуль в `mvp/counterparty-people/` (типы, репозиторий Postgres/память, служба, DTO); ручки `GET/POST/PATCH counterparties/:id/contacts[/:contactId]`, `GET/POST/PATCH counterparties/:id/employees[/:employeeId]`, `POST counterparties/:id/employees/bulk` (частичный успех); связь сотрудника со слушателем (`learnerId` в правке сотрудника, ставит `Learner.counterpartyEmployeeId` в снимке); аудит.
- **14.2 (фронт):** карточка компании вкладками (Основное · Контакты · Сотрудники), таблицы и формы, вставка сотрудников списком с отчётом по строкам.
- **14.3 (приглашение представителя):** `POST counterparties/:id/contacts/:contactId/invite` — учётная запись по почте, привязка к компании и роль `counterparty_rep` одной транзакцией, письмо входа; решение о месте в лимите сотрудников тарифа.

## Global Constraints

- Права только добавляются: чтение — `counterparties.read`, изменения — `counterparties.write` (§12 не вводит отдельного кода).
- Скоуп представителя: чужая компания — 404, как у `GET counterparties/:id`.
- Каждый SQL — с `tenant_id = $1`; многошаговая запись — в транзакции; постраничные выборки — `order by … , id`.
- Сотрудники не удаляются физически (на них ссылается `learning.learners.counterparty_employee_id`): «уволен» — статус.
- Массовое добавление — частичный успех: валидные строки принимаются, отказы поимённо с причиной.

## Решения (журнал РМ трекера)

- **РМ116.** Контакты и сотрудники — в Postgres напрямую, не в снимке; компания проверяется по снимку, её строка досоздаётся проекцией в транзакции записи (родитель не гарантирован проекцией). В режиме памяти — репозиторий в памяти.
- **РМ117.** Уникальность табельного номера — только когда он задан (частичный уникальный индекс вместо `NULLS NOT DISTINCT`); дубль человека (та же фамилия, имя, отчество у той же компании среди работающих) при массовом добавлении — «пропущен: уже есть», а не ошибка всей пачки.
- **РМ118.** `learner_id` у сотрудника — без внешнего ключа (слушатели проецируются из снимка с той же негарантией, что и компании); связь проверяется службой по снимку.

## Review Focus

3. Вставка 50 сотрудников, из них 3 кривые и 2 дубля — 45 заведены, 5 названы поимённо.
4. Два сотрудника без табельного номера у одной компании — оба сохраняются.
5. Связь сотрудника со слушателем другой компании — отказ с понятной причиной.
