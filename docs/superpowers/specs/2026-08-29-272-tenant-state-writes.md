# Программа 272+292 — запись состояния арендатора при нескольких экземплярах

**Дата:** 2026-08-29. **Журнал расхождений:** записи 272 (дефект логики) и 292 (дрейф).
**ТЗ:** аренда (эксплуатация, масштабирование).

## Что не так сегодня

Состояние центра хранится **снимком**: коллекция целиком лежит строками JSONB, а сохранение
делает «удалить коллекцию — вставить заново» (`postgres-mvp-persistence.backend.ts`,
`postgres-documents-persistence.backend.ts`). Порядок «прочитать → изменить → записать»
сериализован замком арендатора `TenantSerialGateway`, и это сделано правильно: чтение
происходит **внутри** критической секции (см. перехватчики запросов и `MvpTenantRunner`).

Но замок держит очередь **в памяти процесса**. Поэтому:

1. **Второй экземпляр за прокси не защищён ничем.** Оба читают одно состояние, оба пишут
   коллекцию целиком — «последний писатель побеждает» стирает чужие изменения ЦЕЛИКОМ и
   молча. Это касается не только номеров, а любых правок.
2. **Уникальность номеров документов держится на проверке в памяти.** Уникальный индекс
   `uq_documents_reservation_number` существует (миграция 0005), но стоит на таблице
   `documents.number_reservations`, в которую боевой путь НЕ ПИШЕТ ВООБЩЕ: рабочая модель
   чтения — `legacy` (снимок JSONB), двойная запись выключена по умолчанию. Индекс не
   защищает ничего, и гонка двух выпусков может дать два удостоверения с одним номером.

Сегодня в проде один экземпляр, поэтому вреда нет. Цена дефекта — запрет на масштабирование,
записанный в §12.1 handoff, и отсутствие последней линии обороны у регулируемой нумерации.

## Решения, которые рассматривались

| Вариант                         | Почему не он                                                                                                                                                                                                                               |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Построчная запись вместо снимка | Правильно «в теории», но это переписывание всего слоя хранения (полсотни коллекций, ленивая раскладка, шифрование ПДн, двойная запись). Риск несопоставим с выигрышем, и «последний писатель побеждает» остаётся — просто на уровне строки |
| Advisory-лок на всю секцию      | Секция = весь запрос (чтение → обработчик → запись). Держать лок значит держать СОЕДИНЕНИЕ весь запрос: пул превращается в потолок общей одновременности приложения. «Нельзя делать походя» — записано в самом журнале                     |
| Повтор запроса при конфликте    | Обработчик уже сделал побочные действия (рендер PDF, письма). Автоматический повтор небезопасен                                                                                                                                            |

## Принятое решение

**Две независимые линии обороны, ни одна не требует держать соединение.**

### Линия 1 — версия состояния арендатора (закрывает 292 и общий случай 272)

Таблица `core.tenant_state_versions (tenant_id, scope, version)`, где `scope` — `mvp` или
`documents`. Загрузка запоминает версию на объекте состояния; сохранение в ТОЙ ЖЕ транзакции
делает «увеличить версию, если она всё ещё та, что прочитали»:

```sql
insert into core.tenant_state_versions (tenant_id, scope, version)
values ($1, $2, 1)
on conflict (tenant_id, scope) do update
   set version = core.tenant_state_versions.version + 1, updated_at = now()
 where core.tenant_state_versions.version = $3
returning version
```

Ноль строк в ответе = между чтением и записью состояние изменил кто-то другой. Транзакция
откатывается, запрос отвечает **409** с человеческим текстом. Молчаливой потери больше нет.

**Ложных срабатываний внутри одного процесса не будет**: там чтение и запись уже
сериализованы замком, и версия к моменту записи всегда та же. Проверка «просыпается» ровно
тогда, когда появляется второй писатель — то есть ровно в том случае, ради которого заведена.

Гранулярность — на арендатора целиком, а не на коллекцию: снимок так и устроен, и дробить
его значит обещать больше, чем модель может выполнить.

### Линия 2 — заявка на номер документа в БД (закрывает заголовок 272)

Новая таблица `documents.issued_number_claims (tenant_id, reserved_number, reservation_id)`
с первичным ключом `(tenant_id, reserved_number)`. При сохранении коллекции `reservations`
каждый номер заявляется в этой таблице. Если номер уже заявлен ДРУГИМ резервированием —
транзакция падает, документ не выпускается.

Почему не существующая `documents.number_reservations`: у неё внешние ключи на
`documents.numbering_rules` и `documents.generated_documents`, а боевой путь эти таблицы не
заполняет — вставка упала бы на FK. Заводить нормализованную модель ради одного индекса —
отдельная большая работа; заявке нужны только два поля.

Почему заявка на записи, а не в момент `reserveNumber`: сервис документов работает с
состоянием в памяти и БД не знает; сделать его асинхронным — ощутимая переделка. На записи
гарантия та же (дубль физически не сможет закрепиться), а изменение — локальное.

Резервирования никогда не удаляются, а освобождённый номер переиспользуется ТЕМ ЖЕ
резервированием (`reserveNumber` меняет статус существующей записи), поэтому пара
«номер → резервирование» стабильна, и заявка не мешает переиспользованию.

## Что НЕ входит

- Переход на построчную запись и нормализованную модель (отдельная большая работа).
- Автоматический повтор запроса при конфликте: обработчик уже сделал побочные действия.
- Снятие запрета «второй экземпляр» без нагрузочной проверки: после программы запрет
  становится **условным** — обе линии обороны есть, но живьём в два экземпляра не гоняли.

## Приёмка

1. Тест на гонку ДВУХ независимых сохранений мимо замка: второй получает конфликт, первый
   сохранён целиком (без него линия 1 не доказана).
2. Тест на два резервирования одного номера из разных состояний: второе сохранение падает.
3. Внутри одного процесса конфликтов НЕТ: обычный прогон не краснеет.
4. `pnpm ci:check` — exit 0; живая проверка на настоящем PostgreSQL.
