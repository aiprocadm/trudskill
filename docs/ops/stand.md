# Стенд: перезапуск, журналы, память

Требование ТЗ «Стабилизация, UX и развитие», 1.2 (пункт 4): «зафиксировать, как перезапускать
стенд и где смотреть логи». Проверено на живом стенде 15.09.2026.

## Что где

| Что               | Где                                                                           |
| ----------------- | ----------------------------------------------------------------------------- |
| Адрес             | **lms.ptsfera.online** (перед приложением — пароль nginx, логин `demo`)       |
| Копия репозитория | `~/stands/trudskill` — **отдельная**, не рабочая папка `~/projects/trudskill` |
| Порты             | 3011 сервер, 3012 realtime, 3015 витрина                                      |
| База              | `trudskill_stand` в контейнере `test-postgres`                                |
| Службы            | `lms-backend`, `lms-realtime`, `lms-frontend` — **системные** (`User=aiproc`) |

## Перезапуск без прав администратора

`systemctl --user` здесь **не работает**: юниты системные, и команда отвечает «Unit not found».
`sudo` не нужен — служба перезапускается сигналом своему же процессу, а `Restart=always`
поднимает её обратно через 5 секунд:

```bash
for u in lms-backend lms-realtime lms-frontend; do
  kill "$(systemctl show -p MainPID --value $u)"
done
```

Проверка после перезапуска (путь именно такой, `/health` и `/healthz` дают 404):

```bash
curl -s http://127.0.0.1:3011/api/v1/health/ready   # status: ok, pendingCount: 0
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3015/
```

Миграции накатывает сам сервер при старте (`DB_MIGRATIONS_ENABLED=true`), отдельного шага нет.

## Обновление

Штатным скриптом `~/stands/trudskill/scripts/stand/update-stand.sh`; он же стоит в `crontab`
раз в 10 минут. Скрипт снимает копию `.next`, при осечке откатывается и **перезапускает службы**
сигналом `MainPID`. Журнал обновлений: `~/stands/logs/lms-update.log`.

⚠️ **Влитый PR перезапускает стенд.** Если идёт длинный браузерный прогон против стенда,
вливание своей же ветки оборвёт его на середине: автообновление подхватит коммит и перезапустит
сервер. Проверено 13.09 — `NRestarts` вырос ровно в момент `ECONNREFUSED` в логе обхода.

## Где смотреть журналы

| Источник                | Команда                                                  | Оговорка                                                                                                                                      |
| ----------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Обновления стенда       | `tail -f ~/stands/logs/lms-update.log`                   | читается всегда                                                                                                                               |
| **Падения процесса**    | `tail -f ~/stands/trudskill/apps/backend/logs/crash.log` | путь задаётся `CRASH_LOG_FILE`                                                                                                                |
| Системный журнал службы | `journalctl -u lms-backend -n 200`                       | **нужны права**: без групп `adm` / `systemd-journal` команда отвечает «You are currently not seeing messages from other users and the system» |

**Почему заведён файл падений.** Службы пишут в системный журнал, и он постоянный
(`/var/log/journal` есть). Но прочитать его может только член привилегированной группы —
владелец и агент в неё не входят. То есть запись о падении существует, а человек, которому она
нужна прямо сейчас, её не видит. Файл рядом со стендом эту дыру закрывает и содержит вид сбоя,
время и стек.

Запись о падении **никогда не роняет процесс повторно**: если писать некуда, она молча
пропускается — второе исключение поверх первого скрыло бы настоящую причину.

## Память и пул соединений

Замер под сплошным обходом (102 страницы × 5 ролей с нажатиями), 15.09.2026. Снималось каждые
10 секунд, **635 замеров подряд** — около двух часов непрерывной нагрузки:

| Показатель        | До        | Пик под нагрузкой | После     |
| ----------------- | --------- | ----------------- | --------- |
| Память сервера    | **57 МБ** | **57 МБ**         | **57 МБ** |
| Соединений к базе | 2         | **9 из 10**       | 2         |

**Критерий ТЗ «память возвращается к базовому ±20%» выполнен с запасом: она не выросла вовсе.**
Гипотеза «утечка памяти / незакрытые подписки realtime» на этой нагрузке не подтверждается.

**А вот пул соединений — узкое место.** Один последовательный обход выбирает 9 из 10
соединений. Два таких потока (например, два человека, листающих реестры одновременно) упрутся
в потолок: новые запросы будут ждать свободного соединения до `DB_POOL_CONNECTION_TIMEOUT_MS`
и получат отказ. Это ровно тот симптом, который ТЗ описывает как «503 почти на всех адресах».
Поэтому настройки пула и выведены наружу — поднять потолок теперь можно без правки кода.

**Пул соединений теперь настраивается** (раньше числа были зашиты в `database.service.ts`, и
проверить гипотезу «исчерпание пула» можно было только правкой кода):

| Настройка                       | По умолчанию | Смысл                                        |
| ------------------------------- | ------------ | -------------------------------------------- |
| `DB_POOL_MAX`                   | 10           | сколько соединений держать максимум          |
| `DB_POOL_IDLE_TIMEOUT_MS`       | 30000        | через сколько закрывать простаивающее        |
| `DB_POOL_CONNECTION_TIMEOUT_MS` | 5000         | сколько ждать свободное, прежде чем отказать |

## Ограничение памяти — остаётся владельцу

ТЗ просит «лимит памяти и автоперезапуск». **Автоперезапуск уже есть** (`Restart=always`,
`RestartSec=5`). **Лимита памяти нет**, и поставить его агент не может: юниты лежат в
`/etc/systemd/system/`, туда нужен `sudo`. Команды для владельца:

```bash
sudo systemctl edit lms-backend      # откроется пустой файл-дополнение
# вписать:
# [Service]
# MemoryMax=1G
# MemoryAccounting=yes
sudo systemctl daemon-reload && sudo systemctl restart lms-backend
```

Значение подбирается по замеру: базовый уровень сервера — 57 МБ, поэтому 1 ГБ — это запас в
17 раз, а не впритык. Смысл лимита не в экономии, а в том, чтобы утечка привела к быстрому
перезапуску, а не к «сервер жив, но не отвечает».
