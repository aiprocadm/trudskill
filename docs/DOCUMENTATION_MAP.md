# Карта документации и источников правды (SSOT)

Назначение: **зафиксировать, какой файл главный по какому типу информации**, чтобы не размножать противоречивые дубли между `README`, ТЗ и handoff.

## Принцип

У проекта несколько классов истины — это нормально: нельзя смешивать юридически-смысловое ТЗ, реглад инженерной сессии и точку входа для CI в один «мастер-документ».

### Иерархия при расхождении

1. **Согласовано с заказчиком / протокол** (в т.ч. заполненное [приложение Б](../TZ_TRUDSKILL_BASE.md#47-приложение-б-фиксация-границ-пилота-must--вне-scope) в `TZ_TRUDSKILL_BASE.md`).
2. **Целевые требования к продукту** — [TZ_TRUDSKILL_BASE.md](../TZ_TRUDSKILL_BASE.md) (канон детальных требований) + **три действующих дельта-ТЗ**, разделённых по предмету:
   - [TZ_TRUDSKILL_STABILIZATION_UX.md](../TZ_TRUDSKILL_STABILIZATION_UX.md) — **что делать дальше** (стабилизация, блокеры, UX и развитие; ТЗ от 14.09.2026, фазы 1–18). **Единственный документ с незакрытыми задачами — это активный фронт работ.** Статус — [TZ_STABILIZATION_UX_STATUS.md](./TZ_STABILIZATION_UX_STATUS.md).
   - [TZ_TRUDSKILL_ARENDNAYA_SDO.md](../TZ_TRUDSKILL_ARENDNAYA_SDO.md) — **как это должно себя вести** (поведение, функции, права; эпики A–I, фазы 0–6; **в рамках его эпиков при конфликте деталей приоритет у него** — см. его §15.1). Требования закрыты; остаётся каноном. Статус — [TZ_ARENDNAYA_SDO_STATUS.md](./TZ_ARENDNAYA_SDO_STATUS.md).
   - [TZ_UI_REDESIGN_TRUDSKILL.md](./TZ_UI_REDESIGN_TRUDSKILL.md) — **как это должно выглядеть** (информационная архитектура, визуальный язык, компоненты, тексты интерфейса, ребрендинг UI; фазы 0–8). Требования закрыты (94 из 94); остаётся каноном. Статус — [TZ_UI_REDESIGN_STATUS.md](./TZ_UI_REDESIGN_STATUS.md).

   **Между собой они не конфликтуют, потому что разделены предметом:** объём и приоритет работы задаёт ТЗ стабилизации, форму исполнения — ТЗ редизайна, поведение — «Арендная СДО». Если правка интерфейса требует изменить поведение — это не спор документов, а **отдельное решение владельца** (список таких мест — ТЗ редизайна §4.9). Если новое ТЗ требует поведения **вместо** закрытого требования старого (а не сверх него) — тоже решение владельца, спросить одним сообщением.

3. **Факт реализации в коде** — исходники + тесты; описательно — [LMS_AGENT_HANDOFF.md](../LMS_AGENT_HANDOFF.md) и [TZ_MVP_TRACEABILITY.md](./TZ_MVP_TRACEABILITY.md).
4. **Операционное состояние репозитория для агента** — блок `AI Agent State` в [README.md](../README.md).

## Передача между агентами и фраза «продолжай по ТЗ»

Чтобы разные агенты не расходились в трактовке одной и той же формулировки, используйте **единый порядок чтения** и **двойную фиксацию** итога сессии.

### Что означает «продолжай по ТЗ, смотри документацию»

1. Прочитать блок **AI Agent State** в [README.md](../README.md) — краткая текущая цель и дата.
2. Прочитать [LMS_AGENT_HANDOFF.md](../LMS_AGENT_HANDOFF.md) (§1 дата/ветка, §5 последние пункты, §13 Known Issues, §14/§20 next) — **где остановилась последняя инженерная сессия**: факты, файлы, прогоны тестов.
3. Открыть [**TZ_STABILIZATION_UX_STATUS.md**](./TZ_STABILIZATION_UX_STATUS.md) — активный фронт работ: какая очередь текущая, что сделано / частично / требует сверки / не начато. Если задача владельца по предмету относится к другому ТЗ (правило ниже) — открыть его трекер. Перед стартом фазы — план в `docs/superpowers/plans/` и апрув владельца (ТЗ §13/§15).
   **Если незакрытых задач нет ни в одном трекере и журнал расхождений пуст** — сессия переходит в [режим ревизии](./AUDIT_MODE.md): берётся непройденный класс сверки и ищутся дефекты. Не ждать задачу и не придумывать функциональность.
4. Детальные требования и приёмку сверять с [TZ_TRUDSKILL_BASE.md](../TZ_TRUDSKILL_BASE.md) ([§41](../TZ_TRUDSKILL_BASE.md#41-backlog-укрупнённый) backlog, приёмка [§39](../TZ_TRUDSKILL_BASE.md#39-acceptance-criteria)) и матрицей [TZ_MVP_TRACEABILITY.md](./TZ_MVP_TRACEABILITY.md) (BL → пути в коде).
5. При противоречии текст ↔ код — действовать по **иерархии в начале этого файла** (протокол заказчика выше ТЗ-черновика выше факта кода, если иное не согласовано).

<a id="tz-routing"></a>

### Какое из трёх ТЗ продолжать

**Правило по умолчанию: «продолжай по ТЗ» без уточнения = ТЗ стабилизации и UX.** Вопрос владельцу здесь больше не задаётся: два старых ТЗ закрыты по требованиям, очередь работ есть только в новом. Уточнение переключает маршрут.

| Формулировка владельца                                                  | Куда идти                                                                                                                                                                                                                                                        |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **«продолжай по ТЗ» без уточнения**                                     | [TZ_STABILIZATION_UX_STATUS.md](./TZ_STABILIZATION_UX_STATUS.md) → раздел «Где мы сейчас» → очередь выполнения → [TZ_TRUDSKILL_STABILIZATION_UX.md](../TZ_TRUDSKILL_STABILIZATION_UX.md). Взять **первую незакрытую позицию очереди**, а не понравившуюся задачу |
| «продолжай по ТЗ **по стабилизации / по ревью / по UX / по блокерам**»  | Туда же                                                                                                                                                                                                                                                          |
| «продолжай по ТЗ **по интерфейсу / по редизайну / по UI / по дизайну**» | [TZ_UI_REDESIGN_STATUS.md](./TZ_UI_REDESIGN_STATUS.md) → [TZ_UI_REDESIGN_TRUDSKILL.md](./TZ_UI_REDESIGN_TRUDSKILL.md). Требования закрыты — если незакрытого нет, это **канон формы** для текущей задачи нового ТЗ, а не отдельная очередь                       |
| «продолжай по ТЗ **по аренде / по функциям / по правам**»               | [TZ_ARENDNAYA_SDO_STATUS.md](./TZ_ARENDNAYA_SDO_STATUS.md) → [TZ_TRUDSKILL_ARENDNAYA_SDO.md](../TZ_TRUDSKILL_ARENDNAYA_SDO.md). Так же: канон поведения                                                                                                          |
| **«продолжай по ТЗ» с названной задачей**                               | Задача важнее очереди. Найти её в трекере нового ТЗ; форму взять из редизайна, поведение — из «Арендной СДО»                                                                                                                                                     |
| **Незакрытых задач нет ни в одном трекере и журнал расхождений пуст**   | [**Режим ревизии**](./AUDIT_MODE.md): взять непройденный класс сверки, искать дефекты, находки — в журнал расхождений. **Не спрашивать «чем заняться» и не придумывать функциональность**                                                                        |

Если задача попадает в несколько ТЗ сразу (например, задача 3.1 нового ТЗ перестраивает меню — это и объём, и форма) — вести её по **новому ТЗ**, форму брать из редизайна, а изменение поведения или URL проводить отдельным решением владельца (ТЗ редизайна §14.1 «не трогаем» и `RISK-001`).

**Жёсткий инвариант всех трёх:** `apps/frontend/src/e2e/ia-architecture.e2e.test.ts` остаётся зелёным (правило 0.4 нового ТЗ). Конфликт требования с этим тестом — остановиться и спросить, тест под себя не править.

### После каждой инженерной сессии (обязательно согласованно)

- Обновить **README**: `Current Stage`, `Current Goal`, `Last Completed Task`, `Current Task` / `Next Task`, `Last Updated At`.
- Обновить **LMS_AGENT_HANDOFF**: §1 (дата, при возможности коммит), добавить **новый подпункт в §5** или сжатый лог; при необходимости §6–§12; **§20 Final Status** — актуальный срез.
- Если сессия работала по ТЗ стабилизации и UX — обновить статусы задач, очередь выполнения, чек-лист приёмки и журнал сессий в [TZ_STABILIZATION_UX_STATUS.md](./TZ_STABILIZATION_UX_STATUS.md).
- Если сессия шла в [режиме ревизии](./AUDIT_MODE.md) — дописать строку в **реестр прогнанных классов** (раздел 6 того файла), даже если результат «чисто».
- Если сессия работала по дельта-ТЗ «Арендная СДО» — обновить статусы ФТ и журнал сессий в [TZ_ARENDNAYA_SDO_STATUS.md](./TZ_ARENDNAYA_SDO_STATUS.md).
- Если сессия работала по ТЗ редизайна интерфейса — обновить статусы требований, журнал сессий и **журнал расхождений «код ↔ ТЗ»** в [TZ_UI_REDESIGN_STATUS.md](./TZ_UI_REDESIGN_STATUS.md).

Не держать в README задачи, которые уже закрыты в коде, но не отражены в README: это основной источник ложного «куда продолжать» для следующего агента.
