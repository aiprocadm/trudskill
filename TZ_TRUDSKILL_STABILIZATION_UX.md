**Репозиторий:** `https://github.com/aiprocadm/trudskill` (pnpm + Turborepo, Next.js 15 App Router, React 19, TypeScript, NestJS, дизайн-система `@trudskill/ui` — CSS-переменные и классы `.ui-*`, без Tailwind).
**Источник требований:** ревью пяти кабинетов на стенде `lms.ptsfera.online` от 13.09.2026 (роли: platform_admin, tenant_admin, methodist, manager, learner).
**Дата ТЗ:** 14.09.2026. **Версия:** 3.0.
**Статус:** все ранее открытые вопросы закрыты — решения зафиксированы в разделе «Принятые решения» и встроены в текст задач. Агент их не переоткрывает.
**Язык:** весь код, комментарии, коммиты, названия в интерфейсе — русский (кроме идентификаторов кода).

Номера исходного ревью (Б1, Н3, Э7, С2…) сохранены в скобках у каждой задачи — по ним можно сверяться с оригиналом.

### Структура документа

- **Часть I (фазы 1–9)** — прямые требования из UX-ревью: стабильность, блокеры, навигация, язык, правила экранов, кабинет слушателя, визуал, кабинеты по ролям, безопасность.

## 0. Правила работы для агента

Это не рекомендации, а условия приёмки работы.

1. **План раньше кода.** Перед каждой фазой — файл плана в `docs/plans/<фаза>.md`: что меняем, какие файлы трогаем, что может сломаться. Код не пишется, пока план не одобрен владельцем.
2. **Мелкими шагами.** Один PR = одна задача из этого ТЗ (или одна связная группа). PR на 40 файлов проверить невозможно.
3. **`pnpm ci:check` зелёный** перед каждым PR. Красный CI = работа не сделана.
4. **`ia-architecture.e2e.test.ts` — жёсткий инвариант.** Тест требует «один маршрут ровно в одной группе меню». Любая перестройка навигации обязана оставить его зелёным. Если требование ТЗ конфликтует с тестом — остановиться и спросить, а не править тест под себя.
5. **Предупреждать о ломающих изменениях до их выполнения.** К ломающим относятся: смена URL существующих страниц, переименование ключей cookie/localStorage, смена issuer TOTP, миграции БД, переименование scope `@cdoprof/*` → `@trudskill/*`. Последнее **в это ТЗ не входит вообще** — не трогать.
6. **`LMS_AGENT_HANDOFF.md` обновляется** после каждой завершённой фазы: что сделано, что осталось, какие решения приняты.
7. **Дизайн-система.** Новые и переписываемые экраны используют `@trudskill/ui`. Не наращивать теневой слой `src/components/`. Если нужного компонента в дизайн-системе нет — сначала добавить его туда, потом использовать.
8. **Не выдумывать данные.** Если непонятно, как работает функция, — прочитать код, а не предположить.

### 0.1. Обязательный аудит перед Фазой 1

До написания любого кода агент выполняет аудит и кладёт результат в `docs/audit/ux-review-2026-09.md`:

- карта всех маршрутов: `find apps -name "page.tsx" | sort` → таблица «маршрут → файл → пункт меню → заголовок H1 → роль(и)»;

- список страниц, которые падают, и страниц, которые используют устаревший слой `src/components/`.

Этот аудит — фактическая основа для задач Н3, Н4, Я3, Э6. Без него задачи по унификации делать нельзя.

# ЧАСТЬ I. Требования из UX-ревью

## Фаза 1. Стабильность (блокер всего остального)

Пока платформа виснет и падает, любая работа над интерфейсом бессмысленна: проверить результат невозможно.

### 1.1. (Б1) Зависание вкладки браузера насмерть

**Симптом.** Воспроизводится стабильно, 4 раза за сессию на разных ролях:

| Где                                         | Роль           |
| ------------------------------------------- | -------------- |
| Клик «Настройки» со страницы «Эксплуатация» | platform_admin |
| «Аналитика обучения»                        | platform_admin |
| «Настройки»                                 | tenant_admin   |
| «Подтверждение личности»                    | learner        |

Пункт меню подсвечивается, страница не меняется, ручной ввод адреса не работает, Chrome показывает «Страница не отвечает». Единственный выход — закрыть вкладку. Похоже на бесконечный цикл перерисовки React; общий признак — страница, у которой часть данных не загрузилась.

**Что сделать.**

1. Воспроизвести локально с React DevTools Profiler, найти компонент-источник цикла.
2. Типовые причины проверить в первую очередь: `useEffect` без массива зависимостей или с объектом/массивом в зависимостях, который создаётся заново на каждый рендер; `setState` в теле рендера; ретраи запроса без ограничения; селектор стора, возвращающий новый объект.
3. Поставить общий предохранитель: у слоя загрузки данных — максимум N попыток (предложить N=2) с экспоненциальной паузой, после чего экран показывает ошибку и **останавливается**.
4. Добавить ErrorBoundary на уровне сегмента приложения, чтобы падение одного блока не убивало страницу целиком.

**Критерий приёмки.** Час непрерывной работы во всех пяти кабинетах — ни одного зависания. Автотест: при 100% отказе API страница рендерит состояние ошибки и делает не более N запросов (проверяется счётчиком моков).
**Приоритет:** P0. **Риск:** низкий, изменения локальные.

### 1.2. (Б2) Сервер перестаёт отвечать после нескольких страниц

**Симптом.** За сессию дважды: `503` и белый экран почти на всех адресах, лечится только ручным перезапуском, после которого хватает на 4–5 страниц. Из-за этого не открылись «Госвыгрузки», «Материалы», «Библиотека курсов», «Банки вопросов», «Настройка центра», «Оценивание», временами «Курсы».

**Что сделать.**

1. Снять метрики процесса Node на стенде: RSS/heap во времени, количество открытых соединений к БД, количество активных SSE/WebSocket-подключений (`/realtime/stream/...`).
2. Проверить три гипотезы по порядку: (а) утечка памяти / незакрытые подписки realtime; (б) исчерпание пула соединений к БД; (в) циклы из 1.1 нагружают SSR и кладут процесс.
3. По итогам — исправление + защита: лимит памяти и автоперезапуск процесса (PM2/systemd/Docker `restart: always`), healthcheck-эндпоинт, логирование причины падения в файл, а не только в stdout.
4. Зафиксировать в `docs/ops/stand.md`, как перезапускать стенд и где смотреть логи.

**Критерий приёмки.** Обход всех разделов под всеми пятью ролями подряд, без перезапуска — ни одной ошибки 503. Память процесса после обхода возвращается к базовому уровню (±20%).
**Приоритет:** P0. **Примечание:** это backend/ops, не UI, но блокирует всю остальную проверку. Демонстрировать платформу клиентам до закрытия 1.1 и 1.2 нельзя.

## Фаза 2. Блокеры интерфейса

### 2.1. (Б3) Свои страницы ошибок

**Сейчас.** Ошибка сервера → системный экран браузера: без логотипа, без меню, без объяснения, без «Повторить». Отказ в доступе → `/forbidden`: голое «403 / У вас недостаточно прав для просмотра этой страницы / Вернуться на главную», тоже без шапки и меню. Человек выпадает из системы.

**Что сделать.**

1. Страницы 403, 404, 500/503 и офлайн — в общем оформлении системы: шапка, меню, тот же фон и шрифты. Человек остаётся «внутри».
2. Текст по шаблону «что случилось → что делать сейчас → к кому идти». Для 403: «Этот раздел доступен администратору центра. Если он нужен вам в работе — напишите администратору» + кнопка «Написать администратору» (ведёт в сообщения с преднаполненной темой).
3. На серверных ошибках — кнопка «Повторить».
4. Использовать `error.tsx` / `not-found.tsx` App Router на уровне сегментов с общим макетом.

**Критерий приёмки.** Любая ошибка показывает страницу в оформлении системы, с меню и понятным следующим шагом. Проверено принудительным отключением API.

### 2.2. (Б4) Пункты меню, которые никуда не ведут

**Сейчас.**

| Роль           | Пункт              | Что происходит                                                                     |
| -------------- | ------------------ | ---------------------------------------------------------------------------------- |
| platform_admin | «Настройки»        | Молча возвращает на «Арендаторов платформы», кратко подсвечены два активных пункта |
| tenant_admin   | «Настройка центра» | Молча открывает «Настройки»                                                        |
| tenant_admin   | «Учебный центр»    | Страница 403                                                                       |

**Что сделать.** Правило без исключений: **если роль не может открыть раздел — пункта нет в её меню.** Никаких «покажем, но не пустим».

1. Меню собирается из той же матрицы прав, что и серверный guard (единый источник истины, см. 3.2).
2. Если пункт нужен как «расширьте права» — он рендерится явно заблокированным (серый, курсор-запрет) с подсказкой «Доступно администратору центра».
3. Подсветка активного пункта — ровно одна за раз.

**Критерий приёмки.** Автотест: для каждой роли пройти по всем пунктам её меню — ни один не отдаёт 403 и не делает молчаливый редирект на другой раздел.
**Риск:** меню у ролей визуально «похудеет» — это ожидаемо и правильно.

### 2.3. (Б5) «Вход не выполнен» у вошедшего пользователя

**Сейчас.** На «Обмене данными» — три одинаковых красных сообщения «Вход не выполнен или срок сессии истёк» в теле страницы **плюс три одинаковых всплывашки**, при этом в шапке «Platform Admin». На «Настройках» то же в четырёх блоках («Платёжный провайдер», «Провайдер вебинаров», «Оповещения по СМС», «Видео в курсах»), а соседний блок «Профиль» спокойно показывает логин и почту.

**Что сделать.**

1. Разделить три разные ошибки с тремя разными текстами и действиями:
   - `401` сессия истекла → увести на вход с `returnUrl` на текущую страницу, интерфейс дальше не рисовать;
   - `403` нет прав → сообщение «Этот блок доступен роли X», блок не показывать (см. 5.4);
   - `5xx` / сеть → «Не удалось загрузить. Повторить».
2. Дедупликация уведомлений: одинаковый текст в пределах 5 секунд показывается один раз (ключ = текст + код).
3. Проверить, почему при живой сессии часть запросов получает 401 — вероятно, часть вызовов идёт без токена или с другим клиентом. Это корневая причина, чинить её, а не только вывод.

**Критерий приёмки.** На «Обмене данными» и «Настройках» под platform_admin и tenant_admin нет ни одного ложного сообщения о сессии; дублирующиеся тосты не появляются.

### 2.4. (Б6) Подтверждение личности у слушателя

**Сейчас.** Всплывает «К вашей учётной записи не привязан профиль слушателя. Обратитесь в учебный центр», при этом форма загрузки селфи и паспорта активна.

**Что сделать.** Если профиль слушателя не привязан — форму не рендерить вообще. Показать одно сообщение и кнопку «Написать в учебный центр». Загрузку файлов включать только при наличии привязанного профиля.

### 2.5. (Б7) Курс физически нельзя пройти

**Сейчас.** Слушатель открывает единственный материал и видит: «Текстовый материал станет доступен после расширения backend полем textBody». Второй материал под замком без объяснений. Кнопок «Материал изучен» / «Далее» нет, прогресс «Пройдено 0 из 2 — 0%» сдвинуть нечем.

**Что сделать.** Разделить на две задачи:

**2.5.a — функциональная (backend). Решение Р8: делается сразу, в фазе 2, но в минимальном объёме.** В объём входят три типа материала — текст (хранение и отдача `textBody`, редактирование в простом редакторе), файл (PDF/DOCX на скачивание и просмотр), ссылка на видео. Плюс отметка прохождения материала, пересчёт прогресса курса и правило разблокировки следующего материала. **Вне объёма этой фазы:** SCORM-плеер, защищённое видео со своим хранилищем, учёт академических часов по факту просмотра — это отдельная работа по видео-пайплайну. Обоснование: без трёх базовых типов курс физически непроходим, то есть продукта нет; полный движок при этом растянет фазу 2 на месяцы и заблокирует всё остальное.

**2.5.b — интерфейсная (делается в любом случае).**

1. Кнопка «Материал изучен → Далее» на каждом материале.
2. У замка — подпись причины: «Откроется после изучения "Текст инструктажа"».
3. Ни одной технической фразы на экране слушателя. Если данных нет — «Материал готовится, обратитесь в учебный центр», а не название поля БД.

**Критерий приёмки.** Слушатель проходит курс целиком: материал → отметка «изучено» → следующий материал → тест → результат → документ.

## Фаза 3. Навигация (главная причина «непонятно»)

### 3.1. (Н1) Убрать двухэтажное меню «6 пунктов + Ещё»

**Сейчас.** У tenant_admin 7 строк, под ними «Ещё», а под «Ещё» — 9 групп и ~50 пунктов. Человек видит 6 строк и думает, что в системе шесть разделов.

**Что сделать.** Одно меню без «Ещё»:

- группы видны сразу, по умолчанию свёрнуты, раскрываются кликом;
- открытая группа и активный пункт запоминаются между переходами (localStorage, ключ с префиксом проекта);
- ориентир плотности: 5–9 групп по 3–7 пунктов;
- группа, в которой находится текущая страница, раскрывается автоматически.

**Критерий приёмки.** Слова «Ещё» в навигации нет ни у одной роли. `ia-architecture.e2e.test.ts` зелёный.

### 3.2. (Н4) Меню роли собирается, а не вычитается из общего

**Сейчас.** Меню роли = общее меню минус несколько пунктов. Отсюда: у методиста в группе «Отчёты и выгрузки» остался один пункт — «Госвыгрузки»; у tenant_admin в «Людях и группах» один пункт — «Массовая загрузка»; методист видит «НЭП подписание», «Переаттестацию», «Комиссии», «Журнал выдачи» (работа юриста и делопроизводителя); руководитель видит почти полное админское меню.

**Что сделать.**

1. Для каждой роли описать её работу в 5–8 задачах (файл `docs/ia/roles.md`) и собрать меню под эти задачи.
2. Конфигурация меню — декларативная: маршрут → название → группа → список ролей. Один файл, один источник истины, из него же берётся проверка доступа и подсветка.
3. Группа с одним пунктом схлопывается: пункт поднимается на верхний уровень.

**Критерий приёмки.** Ни у одной роли нет группы с одним пунктом. Состав меню каждой роли зафиксирован снапшот-тестом.

### 3.3. (Н2) Меню — отдельная фиксированная колонка

**Сейчас.** Меню прокручивается вместе с содержимым: раскрыв группы, получаешь страницу в несколько экранов, где слева меню, справа пустота; прокручивая таблицу, теряешь меню.

**Что сделать.** Колонка меню фиксирована, со своей прокруткой (`position: sticky` + `overflow-y: auto`, высота `100dvh`). Кнопка «Свернуть меню» (остаются иконки) с сохранением состояния.

### 3.4. (Н3) Один раздел — одно имя — одно место

**Сейчас — подтверждённые дубли:**

| Одно и то же          | Как называется                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------- |
| `/workspace`          | «Оперативная панель» и «Главная» — два пункта в одном меню                                    |
| `/notifications`      | «Уведомления» в шапке, «Сообщения» в меню, «Центр уведомлений» в заголовке                    |
| журнал обмена данными | «Журнал синхронизации» в меню, «Журнал обмена» в настройках                                   |
| потребление по тарифу | «Использование» в меню, «Потребление» в настройках                                            |
| настройки центра      | «Настройки», «Учебный центр», «Реквизиты учебного центра», «Настройка центра» — четыре пункта |

Плюс: «Комиссии» (`/admin/commissions`) и «Комиссия» (`/academy/commission`) — две разные страницы, отличающиеся одной буквой. «Задания и тесты» / «Тесты» / «Задания» — три пункта на пересекающиеся страницы. «Главная» встречается в меню дважды (точно у tenant_admin и learner); у руководителя «Главная» стоит между «Отчётами» и «Курсами».

**Что сделать.**

1. На основе аудита (0.1) составить реестр разделов `docs/ia/routes.md`: «адрес → одно название → одна группа → роли».
2. Прогнать по реестру: меню, `<h1>`, хлебные крошки, результаты поиска, `<title>`.
3. Дубли либо слить, либо явно развести по смыслу и переименовать так, чтобы разница читалась (например, «Комиссии центра» и «Аттестационная комиссия курса»).
4. Старые адреса при слиянии — редиректом, чтобы не ломать закладки и ссылки в письмах.

**Критерий приёмки.** Ни один адрес не ведёт на два разных названия и ни одно название не ведёт на два разных адреса. Проверяется тестом по реестру.
**Риск:** смена адресов ломает закладки — обязательны редиректы, о списке изменённых адресов предупредить владельца до мержа.

### 3.5. (Н5) Хлебные крошки

**Сейчас.** Карточки заканчиваются словом «Карточка» («Группы / Карточка» вместо «Группы / Группа 360px»). В крошках светятся идентификаторы: «Мои тесты / test_vc8sf4k5 / attempt / Карточка». Попадается технический слаг: «Настройки и система / platform / Арендаторы платформы». У слушателя админские группы: «Главная / Документы и удостоверения / Мой кабинет / Мои документы».

**Что сделать.** Последний элемент — всегда название объекта, полученное с сервера (с плейсхолдером-скелетоном на время загрузки). Идентификаторов, слагов и служебных сегментов (`attempt`, `platform`) в крошках нет. У слушателя своя иерархия, без админских групп.

### 3.6. (Н6) Поиск ищет данные, а не названия разделов

**Сейчас.** `Ctrl+K` ищет только по пунктам меню. «серт» → «Ничего не найдено», хотя есть «Удостоверения» и «Документы». Администратору платформы предлагаются пункты слушателя: «Мой кабинет», «Мои курсы», «Мои тесты».

**Что сделать.**

1. Серверный эндпоинт поиска по данным: слушатели (ФИО, СНИЛС, логин), группы, курсы, компании, документы (номер). Результаты сгруппированы по типам.
2. Синонимы: «серт», «сертификат», «удостоверение», «корочка» → документы. Словарь синонимов — отдельным файлом, чтобы пополнять без правки логики.
3. Фильтрация результатов по правам роли — на сервере, не на клиенте.
4. Пустой запрос показывает подсказку, что можно искать; пустой результат — тоже.

**Критерий приёмки.** Поиск по фамилии слушателя, номеру документа и названию группы находит объект и открывает его карточку. Роль не видит в результатах чужие разделы.

## Фаза 5. Единые правила экранов

Это правила, которые фиксируются один раз в дизайн-системе и применяются ко всем страницам. Сильнее всего влияют на ощущение «удобно». Каждое правило оформляется как компонент/утилита в `@trudskill/ui` + запись в `docs/ui/patterns.md`, а затем раскатывается по экранам.

### 5.1. (Э1) Один набор действий в строке таблицы

**Сейчас:** в «Арендаторах платформы» в каждой строке четыре подчёркнутые ссылки подряд: «Включить работу центра», «Приостановить центр», «Перевести в "В архиве"», «Войти от имени» — опасные красным, обычные синим, всё рядом и всё подчёркнуто.
**Правило:** в строке максимум одно основное действие («Открыть»), остальное — в меню «…». Опасные действия в этом меню внизу, отдельной секцией, красным.

### 5.2. (Э2) Действие соответствует состоянию объекта

**Сейчас:** у опубликованного курса главная кнопка «Опубликовать курс»; в «Моих тестах» «Осталось попыток: 0 из 1» и активная кнопка «Продолжить»; в «Документах» у руководителя пустая колонка «Действия» и кнопка «Создать шаблон».
**Правило:** кнопка отражает текущее состояние («Снять с публикации», «Создать новую версию»); недоступное действие скрывается, а не показывается вхолостую. Проверка возможности действия — на сервере, кнопка — отражение ответа.

### 5.3. (Э3) Подтверждение необратимых действий

**Проверить и добавить, где нет:** «Приостановить центр», «Перевести в архив», «Отозвать лицензию», «Архивировать слушателя», «Закрыть группу», «Завершить тест».
**Правило:** диалог называет объект («Закрыть группу "Группа 360px"?»), называет последствие («Слушателям будут выданы документы, состав группы изменить будет нельзя») и требует осознанного клика. Для самого тяжёлого — ввод названия, **как уже сделано в «Обезличивании» — это эталон, скопировать механику**.

### 5.4. (Э4) Опасное действие — не главная кнопка экрана

**Сейчас:** в карточке группы самая яркая кнопка — «Закрыть группу» (оранжевая, справа вверху).
**Правило:** главная кнопка экрана — всегда конструктивное действие. Необратимое — вторичная кнопка или пункт «…».

### 5.5. (Э5) Панель массовых действий — липкая

**Сейчас:** панель «Выделено: 1 / Архивировать / Снять выделение» появляется под таблицей, ниже пагинации; при длинном списке её не видно. Единственное действие — красное «Архивировать».
**Правило:** панель прилипает к низу экрана при первом выделении, показывает счётчик и 3–5 полезных действий: добавить в группу, назначить курс, выгрузить, архивировать.

### 5.6. (Э6) Один шаблон списка для всех списков

**Сейчас:** «Слушатели» — образцовый список (быстрые отборы, сохранение отбора, выбор колонок, галочки). «Группы» — без поиска и фильтров вообще. «Курсы» — поиск и два фильтра. «Пользователи» — фильтр по роли, но колонки с ролью в таблице нет.
**Правило:** единый компонент списка: поиск → быстрые отборы → фильтры → выбор колонок → таблица → массовые действия. «Слушатели» — эталон, остальные приводятся к нему. Пагинация не показывается, когда страница одна (сейчас «Назад 1/1 Вперёд» висит под списком из одной строки). Колонки соответствуют доступным фильтрам.

### 5.7. (Э7) Разбить «простыни»

**Страницы, где в одну ленту свалено 4–6 несвязанных блоков:**

- «Арендаторы платформы»: таблица центров + здоровье + тарифы + счета аренды + форма создания центра;
- «Документы»: шаблоны + задачи выпуска + нумераторы + подпись и печать;
- «Настройки» tenant_admin: слева список из 15 разделов, справа всё одной лентой, причём часть пунктов слева ведёт на другие страницы, часть прокручивает эту же — предсказать результат клика невозможно;
- карточка курса: версии + нормативные параметры + комиссия + пакет документов + модули + материалы.

**Правило:** вкладки внутри страницы (или отдельные страницы); формы создания — в модальном окне или боковой панели, а не внизу ленты. В «Настройках» — честные вкладки: клик меняет содержимое справа и ничего больше. Активная вкладка отражается в URL (`?tab=`), чтобы ссылку можно было передать.

### 5.8. (Э8) Заблокированная кнопка выглядит заблокированной

**Сейчас:** недоступная кнопка — просто более светлый оранжевый («Отправить на проверку», «Провести тест», «Назначить курс»).
**Правило:** явный стиль «выключено» (серый, `cursor: not-allowed`, контраст по WCAG AA) + подсказка при наведении, чего не хватает: «Загрузите селфи и фото паспорта».

### 5.9. (Э9) Нормальная загрузка файлов

**Сейчас:** системное «Выбрать файл / Файл не выбран» — без превью, перетаскивания, съёмки с камеры и без указания ограничений.
**Правило:** компонент загрузки: перетаскивание, «Сделать фото» на мобильном (`capture="user"`), превью, требования к файлу текстом (формат, размер), прогресс, понятная ошибка. Особенно критично на «Подтверждении личности» — селфи делают с телефона.

### 5.10. (Э10) Режим «только просмотр» виден

**Сейчас:** в карточке курса написано «Версия опубликована — параметры доступны только для просмотра», а поле «Часы (академические)» выглядит как обычное поле ввода со значением 16.
**Правило:** в режиме просмотра значения выводятся текстом, а не в полях ввода; рядом кнопка «Создать новую версию, чтобы изменить».

### 5.11. (Э11) Страница не едет вбок

**Сейчас:** карточка курса в окне 1560 px имеет ширину 2343 px; колонки «Вид» и «Минимум просмотра» уезжают за экран.
**Правило:** горизонтальная прокрутка на уровне страницы запрещена. Широкие таблицы прокручиваются внутри своего блока, первая колонка закреплена.
**Критерий приёмки:** ни одна страница не прокручивается по горизонтали при ширине окна 1280 px (автотест на ширину `document.body`).

### 5.12. (Э12) Мелочи, которые раздражают каждый день

1. **Даты без времени.** В «Журнале действий» только «13.09.2026» — порядок событий внутри дня не прочитать. Нужны дата и время.
2. **Журнал забит мусором.** Сотни строк «Сеанс продлён». Не писать продление сессии в журнал (или скрывать по умолчанию) + фильтр по типу события + группировка повторов.
3. **Пустой `<title>`.** У всех страниц заголовок вкладки пуст — видно «lms.ptsfera.online» вместо «Слушатели — Trudskill». Задать шаблон `%s — Trudskill` через `metadata` и обновлять при переходе.
4. **Дублирующийся призыв.** В «Компаниях» одновременно «Добавить компанию» (справа вверху) и «Добавить первую компанию» (в пустом состоянии), обе оранжевые. Оставить одну.
5. **Тройной заголовок.** «Мои документы» → блок «Мои документы» → «Документы пока не выданы». Убрать средний уровень.
6. **Чат — тупик.** Пустой список диалогов без объяснения и без кнопки «Написать». **Решение Р3: убрать из меню всех ролей на этом этапе.** Незаконченная функция хуже отсутствующей. Потребность «слушатель хочет связаться с центром» закрывается кнопкой «Написать в учебный центр» (см. 2.4, 2.1), которая создаёт обращение и уходит письмом администратору (фаза 11). Код чата не удаляется, маршрут закрывается флагом функции.
7. **Диаграмм не видно.** В «Аналитике» блоки «Завершаемость по курсам» и «С какой попытки сдают экзамен» на нулевых данных выглядят как строчки с нулями. Нужны оси, подписи, внятное пустое состояние «Данных пока нет». Исправить обрывок подписи «Блокеры 1 ↑ рост:».
8. **Отчёты и Аналитика дублируют друг друга** — обе считают завершаемость и сдачу экзаменов. **Решение Р4: «Аналитика» — только экранные срезы и графики (смотрю сейчас), «Отчёты» — только формируемые файлы XLSX/PDF (уношу и отдаю).** Общие вычисления выносятся в один слой, чтобы цифры совпадали. На каждом графике в Аналитике — ссылка «Выгрузить в отчёт».
9. **Две главные кнопки рядом.** На «Отчётности» «Скачать сводку KPI» и «Скачать табличные отчёты» обе выглядят основными — оставить одну основной.

### 5.13. (Э13) Карточка слушателя: разделить правку и уничтожение

**Сейчас:** боковая панель содержит форму профиля и сразу под ней «Обезличивание данных (152-ФЗ)» с пометкой «необратимо»; кнопка «Сохранить слушателя» не закреплена, до неё надо прокручивать.
**Что сделать:** обезличивание — на отдельную вкладку карточки или в меню «…». Кнопки «Сохранить» и «Отмена» закрепить внизу панели. Сам механизм подтверждения (набрать слово «обезличить») сделан правильно — не трогать, использовать как образец для 5.3.

## Фаза 6. Кабинет слушателя

Самый важный кабинет: пользователи не айтишники, заходят раз в год, часто с телефона.

**Что уже хорошо и трогать не надо:** стартовый экран — один крупный заголовок «Начните "Охрана труда…"», одна понятная кнопка «Начать обучение», ниже курсы с прогрессом. Это эталон, сохранить.

### 6.1. (С1) Пять пунктов меню, все на виду

**Сейчас:** 7 пунктов сверху + 5 под «Ещё» («Календарь», «Мои задания», «Мои вебинары», «Мои оплаты», «Подтверждение личности»), плюс «Главная» дважды.
**Целевая структура:** **Обучение · Тесты · Документы · Сообщения · Профиль.** «Задания», «Вебинары», «Календарь» — внутрь «Обучения». «Подтверждение личности» и «Оплаты» — в профиль либо всплывают сами, когда требуются.

### 6.2. (С2) Экзамен — отдельный режим

**Сейчас:** тест идёт в обычном интерфейсе: слева меню, сверху поиск, «Уведомления», переключатель темы и кнопка **«Выйти»** прямо над вопросами.
**Что сделать:** отдельный экран экзамена без меню и без «Выйти». В нём: таймер, «Вопрос 4 из 20», список вопросов с отметками «отвечен / пропущен», кнопка «Завершить» — только внизу и только после экрана-сводки. Выход из режима — через явное подтверждение.

### 6.3. (С3) Номер вопроса совпадает со счётчиком

**Сейчас:** заголовок «Вопрос 3. Кто отвечает за инструктаж…», под ним «Вопрос 1 из 3»; дальше «Вопрос 2» / «2 из 3», потом «Вопрос 1» / «3 из 3». Заголовок берёт номер из банка вопросов, счётчик — позицию в попытке.
**Что сделать:** убрать номер из заголовка вопроса, оставить только «Вопрос N из M» (позиция в попытке).

### 6.4. (С4) Нельзя завершить тест вслепую

**Сейчас:** можно пролистать все вопросы, не ответив ни на один, и нажать «Завершить тест» — без предупреждения и сводки. Попытка при этом одна.
**Что сделать:** перед завершением — экран «Вы ответили на 1 из 3 вопросов. Не отвечено: 2, 3» со ссылками на эти вопросы, и только потом «Завершить». Если попытка последняя — сказать об этом прямо в диалоге.

### 6.5. (С5) Замок объяснён, «Далее» есть

См. 2.5.b: подпись у замка «Откроется после изучения "Текст инструктажа"» и кнопка «Материал изучен → далее» на каждом материале.

### 6.6. (С6) Проверка с телефона

Слушатели учатся с телефона, а мобильная вёрстка в ревью не проверялась вообще. Обязательно проверить на реальном устройстве и ширине 360 px: меню, прохождение материала, тест (особенно кнопки «Назад / Следующий вопрос»), загрузку селфи через камеру, «Мои документы».
**Критерий приёмки:** весь путь слушателя (материал → изучено → следующий → тест → результат → документ) пройден на телефоне.

## Фаза 7. Визуальный слой

Интерфейс опрятный, но обезличенный — его не отличить от десятка других админок. Для продукта, который сдаётся в аренду учебным центрам, это минус: центр выбирает в том числе глазами.

### 7.1. (В1) Перестроить шапку

**Сейчас:** самый заметный элемент шапки — «Выйти» (единственная обведённая кнопка). Имя и роль — серый мёртвый текст. «Уведомления» — ссылка, неотличимая от подписи. Переключатель темы («Оформление» + список) занимает место на каждой странице.
**Что сделать:** справа аватар с именем → меню «Профиль», «Оформление», «Выйти». «Уведомления» — колокольчик со счётчиком непрочитанных. Переключатель темы убрать из шапки в профиль. Поиск расширить — это главный инструмент шапки.

### 7.2. (В2) Цвета статусов — фирменные

**Сейчас:** насыщенно-зелёный «Действующий», серый «Пробный», красный «Заблокирован», оранжевый «В архиве» — палитра «из коробки», не связанная с индиго `#3B4FE4` и кораллом `#FF7A45`.
**Что сделать:** приглушённые фоновые бейджи с тёмным текстом, 4–5 фиксированных значений (нейтральный / успех / внимание / ошибка / выключено), одинаковых во всей системе, как токены дизайн-системы. Проверить контраст в светлой теме — серый текст в шапке на белом читается плохо (цель WCAG AA).

### 7.3. (В3) Экран загрузки

**Сейчас:** серый прямоугольник «Проверяем сессию…» в левом верхнем углу пустой белой страницы — выглядит как сломанная страница.
**Что сделать:** логотип по центру + скелетон будущей страницы (полосы на месте меню, шапки, таблицы).

### 7.4. (В4) Дать интерфейсу характер

1. **Шрифт с характером для заголовков. Решение Р5: пара Onest (заголовки) + Inter (текст).** Onest — свободная лицензия SIL OFL, полноценная кириллица, современный характер без вычурности; Inter остаётся для текста, поэтому читаемость таблиц не меняется. Подключать локально (self-host, `font-display: swap`, подмножество кириллицы+латиница), а не через внешний CDN — это требование и скорости, и независимости от иностранных сервисов. Запасной вариант, если Onest не подойдёт визуально: Golos Text (тоже OFL, кириллица).
2. **Индиго — доминанта, коралл — редкий акцент.** Сейчас коралл расходуется на все кнопки подряд, включая опасные. Акцент, который везде, — уже не акцент.
3. **Глубина вместо плоских карточек:** аккуратные тени, тонкие рамки, больше воздуха между блоками.
4. **Оживить переходы:** появление боковой панели, смена вкладки, подсветка сохранённой строки. Это не украшательство, а ощущение «система откликается». Уважать `prefers-reduced-motion`.
5. **Брендирование арендатора должно работать полностью:** цвет центра подставляется не только в шапку, но и в кнопки/акценты, с автоматическим расчётом контраста. Известный дефект: `--ui-on-accent` не переопределяется по тенанту — центр с жёлтым фирменным цветом получит белый текст на жёлтом. Починить обязательно.

## Фаза 8. Кабинеты по ролям: что убрать и что добавить

### 8.1. Администратор платформы

**Убрать:** всё, что относится к работе внутри одного центра — «Курсы», «Слушатели», «Группы», «Заказы», «Документы», «Комиссии». Сейчас он это видит, при этом «Обмен данными» открывается с ошибками, а «Настройки» не открываются вовсе — меню превращается в набор ловушек.
**Оставить и усилить:** арендаторы, тарифы, счета, лицензии, здоровье платформы, аудит, эксплуатация. Внутрь центра он попадает только через «Войти от имени» — механизм уже есть и сделан правильно (с записью в аудит), его сохранить.
**Добавить на панель:** количество центров по статусам, у кого заканчивается оплата, где встала очередь задач, кто не платит дольше отсрочки.

### 8.2. Администратор учебного центра

Основной пользователь платформы. Для него важнее всего: 3.1 (одно меню), 3.4 (четыре места с настройками → одно), 5.7 (разбить простыни), 2.3 (ложные «вход не выполнен»).
**Добавить: мастер первого запуска. Решение Р6 — семь шагов, из них пять обязательных:**

| №   | Шаг                     | Обязателен | Почему                                                         |
| --- | ----------------------- | ---------- | -------------------------------------------------------------- |
| 1   | Реквизиты центра        | да         | без них документ не сформировать                               |
| 2   | Лицензия / аккредитация | да         | основание деятельности                                         |
| 3   | Аттестационная комиссия | да         | протокол проверки знаний без неё недействителен                |
| 4   | Шаблон удостоверения    | да         | итог всего процесса                                            |
| 5   | Нумератор документов    | да         | номер в реестре                                                |
| 6   | Подпись и печать        | нет        | можно добавить позже, документ выпускается без них в черновике |
| 7   | Первый курс             | нет        | часто берётся из общей библиотеки                              |

Индикатор «5 из 7 готово» на панели, возврат к незавершённому шагу, и **запрет выдачи документов, пока не закрыты обязательные шаги** — с понятным объяснением, а не молчаливой ошибкой.

### 8.3. Руководитель

Самый недоделанный кабинет: нет своей стартовой страницы (попадает сразу в «Группы»); видит страницу настройки шаблонов документов, нумераторов и печатей, где ничего не может сделать (колонка «Действия» пустая), но кнопка «Создать шаблон» на месте; под «Ещё» — почти полное админское меню.
**Что сделать:** собрать кабинет с нуля вокруг вопросов «как идёт обучение по моим компаниям», «кто не успевает», «что горит по срокам», «сколько выдано документов». Состав: Панель · Компании · Группы · Слушатели · Отчёты. Всё остальное убрать.

### 8.4. Методист

- Стартовый экран наполовину состоит из «нет доступа» (см. 4.4).
- Ядро его работы — «Материалы», «Библиотека курсов», «Банки вопросов» — не открылось вообще (см. 1.2), после починки сервера проверить отдельно.
- Карточка курса едет вбок (5.11) и свалена в одну ленту (5.7).
- «Модули» и «Материалы модуля» — два отдельных блока, модуль приходится повторно выбирать в выпадающем списке.
- Видит «НЭП подписание», «Переаттестацию», «Госвыгрузки» — не его работа (см. 3.2).

**Что сделать:** карточка курса на вкладках (**Параметры · Программа · Аттестация · Документы**), где «Программа» — дерево «модуль → материалы» с перетаскиванием, а не два независимых блока. Плюс кнопка **«Посмотреть глазами слушателя»** — без неё методист не может проверить свою работу.

### 8.5. Слушатель

См. Фазу 6 целиком. Коротко: стартовый экран отличный, дальше — обрыв.

## Фаза 9. Безопасность (не UX, но зафиксировано)

1. **Токен доступа в адресе запроса:** `/realtime/stream/user%3Au_tenant_admin?since=...&access_token=eyJhbGci...`. Адреса попадают в логи nginx, историю браузера и заголовок `Referer`. Передавать токен в заголовке или в защищённой httpOnly-cookie. Для SSE, где заголовки недоступны, — одноразовый короткоживущий тикет вместо полноценного токена.
2. **Двухфакторная защита выключена** у администратора центра («Настройки → Профиль»). **Решение Р7: 2FA обязательна для ролей «Администратор платформы» и «Администратор центра», внедряется в три шага.** (1) Сейчас: 2FA доступна и предлагается баннером в профиле. (2) Через 30 дней после релиза фазы 17: при входе админ видит экран «Подключите двухфакторную защиту» с возможностью отложить не более трёх раз. (3) Далее — вход без 2FA для этих ролей невозможен. Для остальных ролей 2FA остаётся добровольной; слушателю не навязывается никогда. Issuer TOTP при этом **не меняется** — иначе слетают уже привязанные приложения.

## Фаза 10. Надёжность обучения и экзамена

Самая опасная зона продукта. Слушатель проходит экзамен один раз, с телефона, часто на плохой связи, и по результату получает удостоверение, которое уходит в реестр Минтруда. Любая потеря данных здесь — это не «неудобство», а спор с человеком и риск для аккредитации центра.

### 10.1. Автосохранение ответов и восстановление попытки

**Проблема.** Сейчас (по коду проверить обязательно) ответы, судя по поведению интерфейса, удерживаются на клиенте до завершения теста. Если у слушателя закрылась вкладка, разрядился телефон, пропала связь или сервер отдал 503 (см. 1.2) — попытка потеряна. Попыток при этом бывает **одна** (см. 6.4).

**Что сделать.**

1. Каждый ответ отправляется на сервер сразу при выборе, с идемпотентным ключом (`attemptId + questionId`). Ответ хранится на сервере, а не в памяти вкладки.
2. При повторном входе в незавершённую попытку — восстановление: «Вы продолжаете попытку, начатую в 14:32. Отвечено 7 из 20».
3. Офлайн-очередь: при пропаже связи ответы копятся локально, показывается индикатор «Нет связи, ответы сохранятся при восстановлении», при возвращении сети — досылаются.
4. Явный индикатор состояния сохранения рядом с вопросом: «Сохранено» / «Сохраняем…» / «Не сохранено — проверьте связь».

**Критерий приёмки.** Тест: на середине попытки принудительно перезагрузить страницу, закрыть вкладку, отключить сеть на 30 секунд — ни один ответ не потерян, попытка не сгорела, счётчик попыток не увеличился.
**Приоритет:** P0 внутри части II.

### 10.2. Таймер и серверное время

**Проблема.** Если таймер экзамена считается на клиенте, его можно обойти переводом системных часов, а при перезагрузке страницы он может обнулиться или, наоборот, «съесть» время.

**Что сделать.** Срок окончания попытки хранится и проверяется **на сервере**; клиент только отображает остаток, синхронизируясь с сервером. При истечении времени сервер закрывает попытку сам, независимо от того, открыта ли вкладка. Пауза недопустима — если она предусмотрена регламентом, оформить её как явное серверное событие.

### 10.3. Защита от потери несохранённых данных в формах

**Проблема.** В админских формах (карточка слушателя, курс, шаблон документа) можно набрать данные и уйти со страницы кликом по меню — без предупреждения.

**Что сделать.** Единый механизм «грязной формы»: при попытке уйти со страницы или закрыть модальное окно с несохранёнными изменениями — вопрос «Уйти без сохранения?». Для длинных форм (карточка курса, шаблон документа) — черновик, сохраняемый локально с пометкой «Черновик от 14:20, восстановить?».

### 10.4. Понятная страница результата и правила пересдач

**Что сделать.**
**Решение Р9 — модель попыток строится по п. 79 Порядка № 2464, а не по игровой логике «три жизни».** Работник, показавший неудовлетворительные знания, не допускается к самостоятельному выполнению обязанностей и направляется на повторную проверку знаний в течение 30 календарных дней со дня проверки. Отсюда:

1. **Итоговая проверка знаний — одна попытка.** Её результат («удовлетворительно» / «неудовлетворительно») попадает в протокол и в реестр обученных лиц — в том числе при неудовлетворительном результате.
2. **Неудовлетворительный результат не «сжигает» слушателя,** а создаёт в системе задачу «Повторная проверка знаний» с автоматически предложенным сроком — 30 календарных дней. Уведомления слушателю, руководителю и администратору центра (фаза 11); задача попадает в список «Горит по срокам».
3. **Тренировочное тестирование — без ограничения попыток,** с полным разбором ошибок. Это отдельная сущность, в протокол она не идёт.
4. **Разбор ошибок итоговой проверки не показывается** — иначе банк вопросов утекает за несколько попыток. Слушателю показывается процент, порог и темы с ошибками, без правильных ответов.
5. Экран результата содержит: сдано/не сдано, процент и проходной порог, время прохождения, что дальше и в какой срок, кнопку «Написать в учебный центр».

Технические попытки (обрыв связи, перезагрузка страницы) попыткой **не считаются** — см. 10.1.

## Фаза 11. Уведомления и почта

**Проблема.** Почта отключена (`NoopMailer`). Для СДО это значит, что базовые сценарии не работают вовсе: слушатель не получает доступ, никто не узнаёт о сроках, документ выдан молча. Сейчас эту работу делает администратор руками — рассылает логины и звонит.

### 11.1. Матрица событий и каналов

Составить и согласовать таблицу: **событие → кому → по каким каналам → шаблон**. Минимальный набор событий:

| Событие                             | Кому                               | Канал                    |
| ----------------------------------- | ---------------------------------- | ------------------------ |
| Слушателя добавили и назначили курс | слушателю                          | почта (+СМС опционально) |
| Приглашение / доступ в систему      | слушателю                          | почта, СМС               |
| Сброс пароля                        | всем ролям                         | почта                    |
| До окончания срока обучения N дней  | слушателю + руководителю           | почта, в системе         |
| Экзамен не сдан, доступна пересдача | слушателю                          | почта, в системе         |
| Документ выдан                      | слушателю + заказчику              | почта                    |
| Приближается переаттестация         | слушателю, руководителю, админу УЦ | почта, в системе         |
| Заявка/заказ поступил               | админу УЦ                          | в системе, почта         |
| Госвыгрузка завершилась с ошибкой   | админу УЦ                          | в системе, почта         |
| Оплата тарифа / лимит близок        | админу УЦ                          | почта                    |

Каналы: почта, СМС, уведомление внутри системы. Каждый канал включается тенантом отдельно, и у пользователя есть страница «Уведомления» с подписками.

### 11.2. Отправка писем на самом деле

1. Заменить `NoopMailer` на рабочий транспорт. **Решение Р10:** транзакционная отправка через российского провайдера с API и SMTP (базовый вариант — Unisender Go; подходит любой SMTP-совместимый, поэтому транспорт делается сменяемым через настройку, без привязки к вендору в коде). Домен отправки — общий домен платформы с корректными SPF/DKIM/DMARC; имя отправителя подставляется от центра («Учебный центр …»). Свой SMTP центра — опция для старших тарифов. **СМС по умолчанию отключены** и включаются центром за свой счёт: для большинства сценариев писем достаточно, а СМС превращаются в постоянную статью расходов.
2. Шаблоны писем — с логотипом и цветом тенанта (см. 13.3), текст на русском, тон совпадает с интерфейсом.
3. **Журнал отправок**: что, кому, когда, статус (отправлено / отклонено / ошибка), с возможностью повторить. Без него диагностика «слушатель не получил письмо» невозможна.
4. Защита от случайной массовой рассылки с тестового стенда: на нерабочем окружении — перехват всех писем в лог или на один адрес.

### 11.3. Напоминания о сроках

Фоновая задача, раз в сутки: находит обучения с приближающимся сроком и переаттестации, шлёт уведомления по матрице 11.1. **Решение Р11 — пороги по умолчанию:** окончание срока обучения — за 14, 3 и 1 день; переаттестация — за 60, 30 и 7 дней; повторная проверка знаний после неудовлетворительного результата (см. 10.4) — за 14, 7 и 3 дня до истечения 30-дневного срока. Пороги настраиваются центром, но значения по умолчанию заданы именно так: 60 дней для переаттестации — это срок, за который предприятие реально успевает согласовать бюджет и отправить людей. Не более одного письма в день на человека: несколько поводов объединяются в одно. Результат работы виден в разделе фоновых задач с понятным названием, а не как «джобы» (см. 4.2).

## Фаза 12. Массовые данные: импорт и выгрузки

Администратор учебного центра заводит не одного слушателя, а список из 60 человек от предприятия. Это его самая частая и самая болезненная операция.

### 12.1. Мастер импорта слушателей

**Что сделать.**

1. Скачиваемый шаблон XLSX с примером заполнения и пояснением каждой колонки.
2. Загрузка → **предпросмотр**: таблица распознанных строк, подсветка проблемных.
3. Построчная валидация с человеческим текстом ошибки: «Строка 14: СНИЛС указан неверно (нужно 11 цифр)», «Строка 22: такой слушатель уже есть — обновить данные или пропустить?».
4. Импорт выполняется только после подтверждения; частичный импорт допустим, но итог показывается явно: «Загружено 58, пропущено 2 — скачать отчёт об ошибках».
5. Сразу после импорта — предложение следующего шага: «Добавить всех в группу» / «Назначить курс».

### 12.2. Единый механизм фоновых операций

Импорт, выгрузка, госвыгрузка, массовая выдача документов — всё это долгие операции. Сейчас каждая ведёт себя по-своему.

**Правило.** Долгая операция ставится в очередь и показывается одинаково: «Задача выполняется, можно продолжать работу», прогресс, уведомление при завершении, результат в разделе «Фоновые задачи» с возможностью скачать файл или отчёт об ошибке. Пользователь не должен держать вкладку открытой.

### 12.3. Госвыгрузки и ФРДО — статус вместо тишины

Раздел госвыгрузок в ревью не открылся вовсе (см. 1.2), поэтому после починки проверяется отдельно. Требования: видно, что и когда выгружено, что принято, что отклонено и по какой причине, кнопка «Повторить» для отклонённых, и — главное — **список записей, которые выгрузить нельзя, с указанием чего не хватает** (нет СНИЛС, нет подписанного документа). Это прямая защита центра при проверке.

## Фаза 13. Мультитенантность как товар

Платформа сдаётся в аренду другим учебным центрам. Значит, часть работы, которую сейчас делает владелец руками, должна делать система.

### 13.1. Подключение нового центра

Сейчас центр заводится администратором платформы, а «Настройка центра» просто перекидывает на «Настройки» (см. 8.2). Целевое: заявка на подключение → создание центра → мастер первого запуска (8.2) → пробный период → переход на тариф. Каждый шаг виден и центру, и администратору платформы.

### 13.2. Тариф, лимиты и потребление — видимые пользователю

**Решение Р12 — модель тарификации: месячная подписка по числу активных слушателей.** Активный слушатель = уникальный человек, который в расчётном месяце начал обучение или получил документ. Почему так: величина прямо связана с выручкой учебного центра, поэтому цена воспринимается как справедливая и растёт вместе с клиентом. Оплата «за место в системе» штрафует за архив, «за документ» провоцирует занижение, фиксированная подписка невыгодна малым центрам. Дополнительно тарифицируются только СМС (см. Р10) и место под файлы сверх пакета.

**Решение Р13 — поведение при превышении лимита: мягкая блокировка.** При 80% — предупреждение в системе и письмом; при 100% — письмо и баннер; при превышении **прекращается только добавление новых слушателей и запуск новых групп**. Никогда не прекращаются: доступ уже обучающихся к материалам и экзаменам, выдача документов по завершённому обучению, выгрузки в реестр. Обоснование: заблокировать выдачу удостоверения человеку, который уже отучился, — значит подставить центр перед его клиентом и гарантированно потерять арендатора.

**Что сделать.** Страница «Тариф и потребление» у администратора центра: что входит в тариф, сколько израсходовано (активные слушатели, документы, место, СМС), сколько осталось, когда следующее списание, и текстом — что произойдёт при превышении.

### 13.3. White-label по-настоящему

Сейчас брендирование частичное и с дефектом контраста (см. 7.4.5). **Решение Р14 — глубина white-label по тарифам.** Базово всем: поддомен вида `центр.trudskill.ru`, логотип, цвета с автоматической проверкой контраста, название центра в интерфейсе и в имени отправителя писем, реквизиты и подпись в документах. На старшем тарифе: собственный домен центра (подключение по CNAME, сертификат выпускается автоматически) и собственный SMTP. Полное сокрытие платформы («как будто это их собственная разработка») не предлагается: оно удваивает поддержку и лишает продукт узнаваемости. Чек: центр с жёлтым фирменным цветом получает читаемый текст на кнопках, а не белый на жёлтом.

### 13.4. Изоляция данных — с доказательством

**Что сделать.** Автотесты, доказывающие, что тенант A не может получить данные тенанта B: перебор основных эндпоинтов с чужими идентификаторами, проверка поиска (см. 3.6 — новый поиск по данным легко становится дырой), проверка выгрузок и файлов в хранилище. Этот тест обязателен в CI: любая новая ручка проверяется на изоляцию.
**Приоритет:** P0 внутри части II — утечка между центрами для арендной модели фатальна.

### 13.5. Режим «Войти от имени»

Механизм есть и сделан правильно (с записью в аудит), но в интерфейсе он невидим. Добавить: постоянная заметная полоса сверху «Вы работаете от имени центра "…" под ролью "…" — Выйти из режима», запрет необратимых действий в этом режиме (или отдельное подтверждение с пометкой), и отметка в журнале, что действие совершено администратором платформы, а не сотрудником центра.

## Фаза 14. Доступность и работа с телефона

Заявленная цель проекта — WCAG AA, но в ревью доступность не проверялась вообще, а мобильную вёрстку проверить не удалось. При этом слушатели учатся с телефона, а среди них есть люди с плохим зрением — для обучения по охране труда это обычная аудитория.

### 14.1. Доступность (WCAG AA)

1. Вся работа возможна с клавиатуры: переходы по Tab в логическом порядке, видимое кольцо фокуса, «Пропустить к содержимому», Esc закрывает модальные окна, фокус возвращается на кнопку-источник.
2. У каждого поля есть связанный `label`; ошибка формы связана с полем и озвучивается (`aria-describedby`, `aria-invalid`).
3. Модальные окна и выпадающие меню — с корректными ролями и ловушкой фокуса.
4. Контраст текста и элементов — не ниже AA (в ревью отмечен серый текст в шапке на белом).
5. Смысл не передаётся одним цветом: у статусов есть текст, у ошибок — значок и подпись.
6. Автоматическая проверка (axe) в CI на ключевых экранах + ручная проверка клавиатурой.

### 14.2. Реальная адаптивность

1. Брейкпоинты и проверка на 360 / 768 / 1280 px. На 360 px — ни одной горизонтальной прокрутки.
2. Мобильное меню (выдвижная панель), шапка с сокращённым набором.
3. Широкие таблицы на телефоне превращаются в карточки со значимыми полями, а не сжимаются до нечитаемости.
4. Область нажатия кнопок и чекбоксов — не меньше 44×44 px; учтены безопасные зоны (вырез, нижняя панель).
5. Формы: правильные типы клавиатуры (`inputmode` для СНИЛС, телефона, почты), автозаполнение.

### 14.3. Экзамен на телефоне

Отдельный сценарий проверки: кнопки «Назад / Следующий вопрос» не уезжают под панель браузера, длинный вопрос прокручивается, таймер виден всегда, загрузка селфи через камеру работает (см. 5.9), обрыв связи не ломает попытку (см. 10.1).

### 14.4. Уважение к настройкам пользователя

`prefers-reduced-motion` отключает анимации (см. 7.4.4); интерфейс не ломается при масштабе 200% и при системном крупном шрифте.

## Фаза 15. Производительность и наблюдаемость

Фаза 1 чинит текущее падение. Эта фаза делает так, чтобы следующее падение первым увидел разработчик, а не клиент.

### 15.1. Сбор ошибок фронта и бэка

**Что сделать. Решение Р15: сбор ошибок разворачивается на собственном сервере в РФ (GlitchTip или Sentry self-hosted), а не в иностранном облаке.** Причина не в цене: в трассировки неизбежно попадают адреса страниц с идентификаторами слушателей и фрагменты данных, то есть персональные данные, — их передача во внешнее облако создаёт риск по 152-ФЗ. Дополнительно включить маскирование СНИЛС, ФИО, почты и токенов до отправки события. Собираются: необработанные исключения, ошибки запросов, срабатывания ErrorBoundary (см. 1.1). Сквозной идентификатор запроса (`X-Request-Id`), который виден и в логах, и на экране ошибки — чтобы пользователь мог назвать номер, а разработчик найти случай.
**Делается вместе с фазой 1**, иначе проблемы 1.1 и 1.2 нечем диагностировать.

### 15.2. Метрики, здоровье и дежурство

Эндпоинт здоровья (БД, очередь, хранилище, почта), базовые метрики (память, время ответа, ошибки 5xx, длина очереди), оповещение владельцу при падении, и `docs/ops/runbook.md`: что делать при 503, где логи, как перезапустить, как откатить релиз.

### 15.3. Бюджеты производительности

**Решение Р16 — бюджеты зафиксированы и проверяются в CI (превышение = красная сборка):**

| Показатель                                | Бюджет   | Почему столько                                             |
| ----------------------------------------- | -------- | ---------------------------------------------------------- |
| Начальный JS (gzip) на страницу           | ≤ 300 КБ | слушатель открывает курс с телефона на мобильном интернете |
| LCP типовой страницы списка (эмуляция 4G) | ≤ 2,5 с  | порог «быстро» по Core Web Vitals                          |
| Ответ основных API, p95                   | ≤ 500 мс | ниже порога заметной задержки в таблицах                   |
| Записей на страницу списка по умолчанию   | 50       | компромисс между прокруткой и нагрузкой                    |
| Сохранение ответа на экзамене, p95        | ≤ 300 мс | иначе индикатор «Сохранено» раздражает                     |

Правило: страница со списком не грузит все записи разом — серверная пагинация; таблицы длиннее 200 строк виртуализируются.

### 15.4. Запросы к базе

Проверить основные списки и отчёты на N+1 и отсутствующие индексы (слушатели, группы, документы, журнал действий). Журнал действий, забитый строками «Сеанс продлён» (см. 5.12.2), — первый кандидат на проблему с объёмом.

### 15.5. «Сообщить о проблеме»

Кнопка в меню профиля: отправляет обращение с автоматически приложенным контекстом (адрес страницы, роль, идентификатор запроса, версия сборки). Для арендной модели это дешевле любой поддержки по телефону.

## Фаза 16. Защита от регрессий

Без этого раздела всё сделанное в фазах 3–5 расползётся обратно за два месяца, потому что унификация держится на дисциплине, а дисциплина — на проверках.

### 16.1. Сквозные тесты по ролям

Smoke-тест на каждую из пяти ролей: войти → пройти по всем пунктам своего меню → убедиться, что страница отрисовалась, нет 403, нет молчаливого редиректа, нет горизонтальной прокрутки при 1280 px. Это автоматизация пунктов 1, 2 и 6 чек-листа приёмки.

### 16.2. Снапшот навигации

Состав меню каждой роли и реестр разделов (3.4) фиксируются снапшот-тестом: любое изменение навигации становится видимым в code review, а не обнаруживается пользователем.

### 16.3. Правило «никакой технической лексики на экране»

ESLint-правило (или тест по собранной сборке), запрещающее в пользовательских строках: `noop`, `fake`, `bbb`, `tenant`, `backend`, `textBody`, `Manager`, `Methodist`, `Platform admin`, `Tenant admin`, «тенант», «джобы». Это автоматизация пункта 3 чек-листа.

### 16.4. Тексты как ресурс

Все пользовательские строки выносятся в единый словарь (`ru.ts` или аналог) вместо хардкода в компонентах. Даёт три вещи сразу: единый язык проверяется грепом, названия ролей и разделов правятся в одном месте (4.1, 4.3), и открывается путь к другим языкам, если центр захочет. Плюс короткий `docs/ui/tone-of-voice.md`: как пишем ошибки, пустые состояния, подтверждения.

### 16.5. Ключевой сценарий слушателя — в CI

Автотест полного пути: назначение курса → изучение материала → отметка «изучено» → тест → результат → выдача документа. Это пункт 9 чек-листа, и он самый ценный: именно он ломается чаще всего.

### 16.6. Визуальные регрессии

Скриншот-тесты 8–10 эталонных экранов (список слушателей, карточка курса, экран экзамена, стартовый экран слушателя, настройки) в светлой и тёмной теме.

## Фаза 17. Персональные данные и безопасность сверх ревью

Система хранит ФИО, СНИЛС, паспортные фотографии и селфи. Это чувствительные персональные данные, и требования к ним жёстче, чем к обычному SaaS.

### 17.1. Защита входа

Ограничение частоты попыток входа и восстановления пароля, временная блокировка после серии неудач, журнал входов (когда, откуда, успешно или нет) в профиле пользователя, завершение чужих сессий. Обязательная 2FA для админских ролей — см. 9.2, с учётом предупреждения про issuer TOTP.

### 17.2. Доступ к персональным данным под контролем

1. Журнал доступа: кто открывал карточку слушателя, кто скачивал паспортные фото, кто выгружал списки. Это то, что спрашивают при проверке.
2. Маскирование по умолчанию: СНИЛС и паспортные данные в списках показываются частично, полностью — по явному действию (которое пишется в журнал).
3. **Файлы проверки личности (селфи, фото паспорта). Решение Р17: хранятся 90 дней после выдачи документа, затем удаляются автоматически;** остаётся протокол верификации — кто, когда и с каким результатом проверил, плюс хеш файла. Срок настраивается центром в пределах 30–365 дней. Обоснование: 90 дней покрывают типовой период претензий и проверок, но не превращают платформу в вечное хранилище паспортных сканов — а именно такое хранилище является главным риском при утечке и прямым нарушением принципа минимизации по 152-ФЗ. Удаление выполняется фоновой задачей, факт удаления пишется в журнал.

### 17.3. Права субъекта данных

Согласие на обработку фиксируется с датой и версией текста; политика обработки доступна по ссылке; по запросу субъекта данные выгружаются и обезличиваются (механизм обезличивания уже сделан правильно — см. 5.13, достроить вокруг него сценарий запроса).

### 17.4. Резервные копии и восстановление

**Решение Р18 — регламент резервного копирования:** полная копия БД ежедневно ночью плюс непрерывный журнал транзакций с точкой восстановления не реже часа; файловое хранилище — ежедневно инкрементально; глубина хранения 30 дней, плюс копия на первое число каждого месяца — 12 месяцев. Копии хранятся не на том же сервере, что боевая база. **Целевые показатели: потеря данных не более 1 часа (RPO), восстановление не дольше 4 часов (RTO).** Ежемесячно — учебное восстановление на отдельный стенд с записью результата; непроверенная копия считается отсутствующей. Описать в `docs/ops/backup.md`: что копируется, куда, как часто, как восстановить, кто отвечает.

### 17.5. Базовая гигиена

Заголовки безопасности (CSP, HSTS, `X-Content-Type-Options`), секреты только в переменных окружения и не в репозитории, зависимости проверяются на известные уязвимости в CI, загружаемые файлы проходят антивирусную проверку (ClamAV в проекте уже есть — убедиться, что он включён на всех путях загрузки).

## Фаза 18. Продажи и демонстрация

Мелкая по объёму фаза, но прямо влияет на выручку.

### 18.1. Демо-данные

В ревью диаграммы аналитики выглядели как строчки с нулями, потому что данных нет (см. 5.12.7). **Решение Р19 — состав демо-набора (скрипт наполнения, запуск одной командой):** 2 учебных центра (один образцовый, второй пустой — чтобы показывать мастер первого запуска), 3 компании-заказчика, 5 курсов, 8 групп в разных состояниях (набор, идёт обучение, закрыта), 120 слушателей с реалистичным распределением прогресса (часть не начала, часть учится, часть сдала, часть получила «неудовлетворительно» и ждёт повторной проверки), 90 выданных документов, история за 4 месяца — чтобы графики завершаемости и сроков показывали динамику, а не нули. Данные вымышленные, СНИЛС из тестового диапазона, фотографии — обезличенные заглушки. Без этого платформу невозможно показывать клиенту — аналитика на нулях выглядит как неработающая функция.

### 18.2. Публичная проверка документа

Проверка удостоверения по QR (механизм в проекте есть) должна иметь опрятную публичную страницу: без входа в систему, с логотипом центра, с понятным ответом «Документ действителен / отозван / не найден». Эту страницу видят работодатели и инспекторы — это витрина центра.

### 18.3. Страница статуса и регламент

Публичная страница состояния сервиса и понятный текст о плановых работах. Для арендной модели это часть договорных ожиданий: центр должен знать, куда смотреть, когда «ничего не открывается».

### Три решения, которые стоит перепроверить на живых клиентах

Это не возврат к обсуждению, а честная отметка о том, где решение принято на разумных основаниях, но проверяется только практикой:

1. **Р12 (тарификация по активным слушателям)** — модель хорошая, но конкретная цена и размер пакетов определяются продажами, а не разработкой. В коде тарифы должны быть **данными, а не константами**: смена цены и лимитов не должна требовать релиза.
2. **Р9 (одна попытка итоговой проверки)** — соответствует ПП 2464, но некоторые центры на практике разрешают сразу вторую попытку внутри того же дня. Поэтому число попыток итоговой проверки делается настройкой курса со значением по умолчанию «1», а механика повторной проверки со сроком 30 дней — обязательной в любом случае.
3. **Р17 (90 дней хранения паспортных фото)** — срок выбран по принципу минимизации. Если юрист центра настоит на другом сроке, настройка уже предусмотрена; жёстко зашивать 90 дней в код нельзя.

Общее правило, вытекающее отсюда: **всё, что в этих решениях выглядит как число (сроки, пороги, лимиты, количество попыток), реализуется как настройка со значением по умолчанию, а не как константа в коде.**

## Что в это ТЗ не входит

Чтобы агент не расширял объём самостоятельно:

- переименование scope `@cdoprof/*` → `@trudskill/*` (~235 файлов) — отдельное согласованное ломающее изменение;
- реализация движка рендеринга документов DOCX/PDF (сам выпуск документов — отдельная работа; в этом ТЗ только интерфейс и правила вокруг него);
- SCORM-плеер, защищённое видео со своим хранилищем, учёт академических часов по факту просмотра (см. Р8);
- интеграция с платёжным шлюзом: тарифы, лимиты и счета делаются, автоматическое списание — нет;
- миграции схемы БД, не требуемые задачами выше;
- переписывание архитектуры — платформа требует доработки, а не переписывания; новое кладётся поверх существующего;
- нативные мобильные приложения — адаптивная вёрстка да, приложения нет.
